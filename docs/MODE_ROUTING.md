# 能力档位路由（chat / retrieval / agent）

> 每个回合先判断"这一轮需要哪一档能力"，再决定把哪些工具规格发给模型。
> 少注入工具规格就是省 token：纯聊天不必带 80 多个工具定义。
> 路由**不是权限系统**：它只决定"发哪些工具规格"，审批、白名单、路径边界一律照旧。

## 1. 三档与工具集合

| 档位 | 用途 | 工具集合 |
|---|---|---|
| `chat` | 纯聊天、问既有记忆 | 约 5 个只读记忆工具：`get_time`、`recall`、`search_history`、`journal_view`、`person_lookup` |
| `retrieval` | 查询与检索 | chat 全部 + 全量记忆检索、授权工作区文件、只读命令、公开网页、B站读四件套、系统只读状态（约 22 个） |
| `agent` | 多步任务与实际操作 | 当前场景原有的全部工具（写操作照旧要人工确认） |

实现位置：`core/modes.py`（声明与纯函数）、`core/router.py`（判定）。

### 省了多少

同一注册表快照下的实测（2026-10-31，93 个已注册工具，`estimate_tokens` 口径）：

| 档位 | 工具数 | 工具规格估算 token | 相对完整档位 |
|---|---|---|---|
| agent | 93 | 17540 | — |
| retrieval | 22 | 4036 | 省 77.0% |
| chat | 5 | 887 | 省 94.9% |

证据见 [evidence/mode-routing-2026-10-31.json](evidence/mode-routing-2026-10-31.json)。
这是**工具规格**的节省；路由判定本身还有一次额外模型调用，净收益需真实模型小样本测。

### 现场实测（2026-10-31，重启后对新进程）

同一条输入「你好」，四种档位的**实际 prompt tokens**（供应商上报值）：

| 档位 | 实测输入 tokens | 相对完整档位 |
|---|---|---|
| auto（规则判为 chat） | 619 | 省 94.9% |
| chat | 645 | 省 94.7% |
| retrieval | 1257 | 省 89.6% |
| agent | 12153 | — |

「你好」命中确定性寒暄规则，**路由没有发起模型调用**（用量流水里没有 `route` 条目），所以没有额外成本。

> **生效前提**：档位是服务端行为，必须**重启工作台进程**才会加载新代码；
> 只刷新浏览器页面不生效（页面下拉会照常显示，但后端仍按旧行为跑完整工具集）。

### 档位只缩小能力

```
有效工具 = 档位白名单 ∩ 场景白名单
```

- 场景白名单：所有者私聊=全部；非所有者私聊=`DM_ALLOWED_TOOLS`；群聊=`GROUP_ALLOWED_TOOLS`。
- 因此**群聊即使升到 agent 也拿不到工作区文件与设备工具**——作用域才是上限，档位在内层再收紧。
- 插件与 MCP 工具只在完整档位出现：轻量回合不拉起外部服务，也不会被插件顶名覆盖。

## 2. 判定流程

在 `Agent._chat()` 内、用户消息落库之后、上下文组装之前执行：

1. **显式指定**（请求带 `mode=chat|retrieval|agent`）→ 直接使用，不调模型。
2. **确定性规则**（`core/router.py`）：明确动作意图 → agent；明确只读查询 → retrieval；
   寒暄短句 → chat。高置信输入不额外付出一次模型调用。
3. **模型判定**：规则没把握时，用 `models.router`（留空则 review，再留空则 chat）判定一次。
   输入只有稳定分类提示词 + 当前文本 + 至多 4 条近期原文（逐条截断），
   **不含**完整历史、工具规格、档案或常驻记忆；调用走 Gateway，`purpose="route"`，
   与主调用共用同一份 run 预算与取消信号。
4. **副作用后置守卫**：模型判成 chat/retrieval，但文本里有明确动作意图 → 改判 agent。
   路由不能把"要动手"的请求降级成只读回合。
5. **回退**：路由模型失败或输出不合规 → 回退**完整档位**（宁可多带一批工具规格，
   也不让用户的事做不成）。

失败与降级都记在 `mode_selected` 事件里（`source` 字段：`manual`/`rule`/`router`/`fallback`/`legacy`）。

> 预算拦截（`RunBudgetExceeded`）与取消（`RunCancelled`）在路由阶段照常上抛，
> 不会被"路由失败回退"吞掉后再发一次请求。

## 3. 同回合一次升档

轻量档位若发现当前能力不够，可以请求升档：内核专用工具 `request_mode`。

- **不是普通工具**：不注册进 `ToolRegistry`，因此无法被外部派发、无法被审批绕过，
  也不会被插件或 MCP 顶名覆盖。它只是编排控制，没有外部副作用，不需要人工确认。
- **只能向上**：`chat → retrieval → agent`；`retrieval → agent`。不能降档、不能同级。
- **每回合最多一次**：第二次请求被拒（`escalation_exhausted`）。
- **生效时机**：下一次模型调用起换用新档位。同批其余调用仍按进入该批时的
  禁用集合判定——模型不能借一次升档顺带放行同批的其它工具。
- **不扩大权限**：升档只换"注入哪一档工具规格"，作用域、审批链、路径策略全部不变。

## 4. 模型选择

| 用途 | 取值顺序 |
|---|---|
| 路由判定 | `models.router` → `models.review` → 运行时当前模型 |
| chat 档 | `models.chat_mode` → 运行时当前模型 |
| retrieval 档 | `models.retrieval_mode` → 运行时当前模型 |
| agent 档 | `models.agent_mode` → 运行时当前模型 |

运行时当前模型是 CLI `/switch` 改的那个（默认 `models.chat`）。
各档模型留空时都跟随它，所以不配置也能用；想要"路由用小模型、复杂任务用旗舰模型"
再单独配。

## 5. 配置

```yaml
models:
  router: ""            # 能力判定模型；留空跟随 review，再留空跟随 chat
  chat_mode: ""         # chat 档位模型；留空跟随 chat
  retrieval_mode: ""    # retrieval 档位模型；留空跟随 chat
  agent_mode: ""        # agent 档位模型；留空跟随 chat

mode_routing:
  default_mode: "auto"  # auto / chat / retrieval / agent
  allow_escalation: true # 轻量档位可否在本回合升档一次
```

- 全部入口（Web / CLI / QQ / 心跳）默认 `auto`。
- 设置中心「模型」页可改默认档位、是否允许升档，并给各档单独配模型。
- 配置改动**重启相应入口生效**（与既有设置口径一致）。

## 6. 入口用法

| 入口 | 用法 |
|---|---|
| Web 工作台 | 发送区下拉选择档位（默认"自动"）；随 `/api/chat`、`/api/chat/stream`、`/api/runs` 传递 |
| CLI | `/mode` 查看；`/mode chat\|retrieval\|agent\|auto` 设置当前 REPL 后续回合 |
| QQ | 不传即 auto（全局配置控制）；群聊仍受 `GROUP_ALLOWED_TOOLS` 限制 |
| 心跳 | 不传即 auto；不确定任务回退完整档位；写操作照旧由 `DenyApprover` 拒绝 |
| 委派子任务 | 固定完整档位：委派本身就是多步骤复杂活，不再二次路由 |

未定义的档位在 API 层直接 422，不进内核。

## 7. 事件与回显

- `mode_selected`：请求档位、生效档位、判定来源、理由、路由模型、可用工具数。
- `mode_upgraded`：从哪档升到哪档、理由、模型、工具数。
- `model_start` / `model_end` 带上 `mode`。
- `/api/chat`、`/api/chat/stream`、`/api/runs` 返回 `requested_mode`、`mode`、
  `mode_source`、`escalated`。
- 工作台运行链显示档位选择与升档；助手消息下方显示"档位 检索"这类标签。

## 8. 已知边界

- 档位只是**上下文预算**手段，不是安全边界；安全边界始终是场景作用域 + 风险等级 + 审批。
- 路由模型每次判定是一次额外模型调用：规则覆盖高置信输入以摊薄成本；
  真实净收益（主调用节省 − 路由成本）需用真实模型小样本测，本仓库只做离线机制验证。
- 真实模型的档位判定准确率尚未验收；误判时轻量回合可升档一次，完整档位始终可用。
- 路由只影响**当前回合**的交互工具；回合后 review 与日/周/月整理按各自既有白名单运行。
