# 版本检查、升级与恢复

更新入口位于设置中心 → 关于。产品版本由 `omni.__version__` 单一声明，打包元数据动态读取；
开发版额外显示提交。当前 0.1.0 仍为未发布内测，不因更新功能落地而变成正式发行版。

## 检查与准备

- 正式通道读取固定官方 Gitee 仓库的 Release，按 SemVer 选择非预发行版本；没有 Release
  显示“暂无正式发行版”。开发通道由用户主动选择，跟随 master，但安装固定到完整提交 SHA。
- 默认启动延迟 30 秒检查，24 小时内复用成功结果，此后后台每小时判断是否需要检查；
  关于页可关闭自动检查，手动检查绕过缓存。读取版本和缓存接口不会联网。
- 同版本号不同提交仍可更新。当前领先、分叉、未知基线、网络失败与 Gitee 限流分别显示。
- Git 安装要求官方 HTTPS/SSH origin、干净工作区及可快进关系，不自动 stash 或丢弃本地修改；
  关于页列出需先保存的本地修改。目标提交改变技能等用户目录时阻断自动安装，要求先手动迁移该版本。
- 源码压缩包使用 `omni-build.json` 的版本、提交与逐文件 SHA-256 作为安装基线。
  未带清单的旧包只有与相同版本的正式发行源码完全一致才能自动建立基线；否则仅检查并提供下载指引。
- 准备更新只写独立控制区，不改当前源码或 `.venv`。归档限制大小、文件数量、路径与文件类型；
  `.env`、config、data、skills 和第三方组件不从源码归档覆盖。
- Gitee 公开归档 API 也可能要求登录。遇到 401 或登录页面时，自动使用系统 Git 在独立裸仓库
  获取同一固定提交；压缩包安装无需转成 Git checkout。未安装 Git 时明确提示安装后重试。

## 安装与恢复点

点击“安装并重启”后必须在弹窗确认。系统暂停新业务操作、消息接入、定时任务领取和服务重拉，
等待现有任务结束，默认 120 秒；超时恢复接收任务。本次不会强行取消正在运行的任务。
额外 CLI/工作台、未登记的环境进程、无法核验的服务和未关闭人工终端均阻断升级。

确认全部入口退出、资源回收后，独立的基础 Python 执行器创建私有恢复点，保存受影响 Agent
与外置数据库、配置、环境密钥、技能、修订和插件树。SQLite 使用一致快照并检查完整性。
快照保留原始凭据，只存于本机；它与“创建备份”的脱敏导出是两种不同用途。

随后安装固定源码提交，保留旧 `.venv`，在原位置执行 `uv sync --frozen` 创建新环境。
在隔离副本中演练各 Agent 数据迁移，再以禁止后台模型 worker 和插件加载的维护模式启动新工作台。
源码身份、数据库和服务监听就绪通过后提交事务，恢复普通运行态与常驻服务。
NapCat、ADB、浏览器组件的版本不由此功能升级。

提交前失败则恢复源码、原环境和被迁移数据；快照校验失败或进程未退出时保留维护状态。
事务提交并开放写入后不会自动回滚历史数据，以免覆盖用户刚产生的记忆和任务。
恢复点和失败环境保留在安装控制区，不自动删除含私人数据的记录。

## 中断恢复

正常 Windows 启动入口 `start.bat` / `scripts/start.ps1` 会先检查未完成事务。
需要时调用冻结的恢复执行器，不依赖可能损坏的 `.venv` 或已更新模块：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/update.ps1 -Recover
```

仍在进行的升级由进程租约与执行锁阻止重复恢复。失败时保留
`data/control/updates/operations/<操作ID>/`，查看脱敏状态 JSON；日志及恢复点可能含本机路径，
不要把整个控制目录上传到公开仓库。业务存储根与 Agent 切换不移动安装级更新控制区。

若状态明确为 `command_residual`，先人工核验并结束所记录命令及其后代，再运行
`scripts/update.ps1 -Recover -ConfirmProcessesStopped`。恢复器仍核验入口、环境占用及已记录进程；
该开关只用于用户已经处理完无法自动核验的后代，不会替用户强制结束未知进程。

## 发布源码包

从干净的官方 Git 提交生成带清单的源码包：

```powershell
uv run --no-sync python agent/scripts/build_release.py --output <仓库外的新输出目录>
```

输出源码 ZIP、逐文件版本清单和 ZIP SHA-256。脚本不会创建标签或发布 Gitee Release。
维护者完成全量验证、更新日志和既有发布闸门后，再按所有者决定创建与产品版本一致的标签及发行版。
HTTPS 和固定官方提交提供下载来源约束，SHA-256 用于缓存和内容校验，不宣称已有独立发布签名体系。

## HTTP 与测试

版本 `GET /api/system/version`；缓存 `GET /api/system/updates`；策略
`PUT /api/system/updates/policy`；检查、准备和安装分别为
`POST /api/system/updates/check|prepare|install`；持久进度为
`GET /api/system/updates/operations/{id}`。准备接收 `candidate_id`，安装接收
`operation_id` 和 `confirm=true`，异步操作返回 202。重复准备或安装返回同一操作。
所有接口沿用配对、Host、Origin 和 CSRF 校验，维护期间仍可查询状态。

自动安装首批验收平台为 Windows。测试使用假 HTTP/命令/服务与临时目录，保持默认离线闸门；
真实用户目录、真实常驻服务和线上发行版不由测试操作。
