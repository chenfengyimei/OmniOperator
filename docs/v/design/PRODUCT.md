# PRODUCT.md —— OmniOperator 产品定位与使用场景

> 本文件是 UI/UX 设计任务的输入文档。设计评审、重构与视觉验收前先读它，确保改动服务于真实使用场景，
> 而不是把工作台当成普通 SaaS 后台或营销站来重画。

## 1. 产品是什么

OmniOperator（小鱼）是**运行在本机的个人 Agent 工作台**：所有者通过对话或 Web 界面发起任务，
主 Agent 调度多个专业 Worker Agent，工具调用、审批、运行记录与交付结果统一回到主会话呈现。
默认入口是 V2 工作台（`omni-web`，`http://127.0.0.1:8766`），V1 保留为回退入口（`omni-web-v1`，`:8000`）。

- 使用者：**单一所有者**（本机、个人数据、个人设备），不是多租户团队产品。
- 运行形态：本机常驻服务 + 浏览器界面；无账号体系、无 SaaS 订阅、无营销页。
- 技术形态：无构建、原生 ES 模块 + 手写分层 CSS，改完刷新即生效（见 `docs/v/reference/UI_DESIGN_SYSTEM.md`）。

## 2. 核心模型（界面必须如实呈现）

1. **一个主会话**：所有者始终在同一个主会话里工作；Worker 的进度、工具调用、状态与结果由主会话统一呈现。
2. **主 Agent + 多 Worker**：主 Agent 负责计划、派发与汇总；Worker 有独立运行、可并行、可互相通信。
3. **动作需要审批**：工具与外部动作默认逐动作审批；审批、打断、停止、恢复、重试是高频操作。
4. **状态必须真实**：未知就是未知（`unknown`、`pending`、`unsettled` 不得显示成成功）；副作用可能已发生时不得假装未发生。
5. **可恢复性优先**：断线、超时、迟到响应、切换 Agent/会话都可能发生，界面要能说明当前看到的是哪一次运行的结果。

## 3. 主要使用场景（决定信息架构）

| 场景 | 用户要完成的事 | 关键界面（V2 既有 26 页） |
| --- | --- | --- |
| 对话与运行 | 发起任务、看流式输出、看调用链与档位、停止/重试 | 对话（chat）、运行检查器 |
| 审批与核查 | 批准/拒绝动作，核对未知副作用的真实结论 | 审批卡片、动作核查、投递核查、终端核查 |
| 记忆与知识 | 事实整理、语义链接、文档上传与检索、反思审阅 | 记忆、文档、反思信笺、人物与档案 |
| 设备与终端 | 观察/操作桌面、安卓、终端会话 | 桌面能力、安卓设备、所有者终端 |
| 调度与投递 | 定时任务、草稿审批、交付回执与归档 | 持久调度、持久投递 |
| 扩展与运维 | 插件信任与授权、MCP、模型接入、诊断与审计 | 可信插件、MCP、模型接入、诊断日志、审计记录 |
| 配置 | 上下文/技能/记忆系统、人设、路由与预算、凭据 | 设置（页内分区） |

## 4. 使用环境与约束

- **主视口 1440×900 桌面**；实际会用到 1024 笔记本、760 平板与 390 手机（应急查看与审批）。
- 会话可能很长（数十万 token），列表可能上百条：**分页、有界列表、显式刷新**是设计前提。
- 长任务与后台任务：进度靠轮询/事件失效通知，不承诺 WebSocket 常连；界面要能在断线后自愈说明。
- 所有数据在本机：**不得**把截图、会话、日志、凭据上传到外部服务；截图只做本机证据。

## 5. 设计目标（本次 UI/UX 增强的成功标准）

1. **成熟商业级 AI Agent 产品的观感**：视觉统一、层级清楚、密度可控、动效克制、深浅双态一致。
2. **状态可读**：主会话、Worker、工具调用、审批、恢复五类状态一眼可辨，且与真实后端状态一致。
3. **恢复可见**：迟到响应、断线、未知结果、冲突（revision/epoch）都有明确文案与下一步动作。
4. **改造不降级功能**：不得为美观删除既有能力（26 页、审批横幅、右栏检查器、终端、四态）。
5. **可维护**：改动用既有 token 与组件，不新增第二套色板/字号/断点/弹窗实现。

## 6. 非目标

- 不做营销首页、landing page、品牌官网（官网在 `website/`，独立静态站，不入库）。
- 不做多租户 SaaS、团队协作、公开注册、移动原生 App。
- 不更换技术栈（不引入 React/Tailwind/构建器）、不改数据库与 API 契约。
- 不以「看起来更现代」为理由重写业务逻辑或删除功能。
