# V3-1 三方向设计对照

本文依据已有三份参考结果整理，比较对象是本地静态原型。可通过 `python -m http.server 8773 --bind 127.0.0.1 --directory WorkWeb` 启动预览，历史对照入口为 /comparison/，其参数为 `?direction=a|b|c&theme=light|dark`。所有会话、Worker、审批和文件均为本地合成样例。

## A · 精密主会话

布局以单一主会话为轴，左侧会话列表、右侧 Inspector 承载检查与证据，中间保持连续阅读宽度。浅色主题是纸白与低饱和墨色，深色主题转为暖墨黑底和浅青强调；两者都用细边线与留白分层，不依赖重阴影。窄屏收拢侧栏，更窄时把 Inspector 移到主内容下方，并压缩输入区、保留可触达的草稿按钮。空状态用“没有匹配会话”“尚未生成”等明确句子解释原因并给出下一步。

## B · 控制台

布局突出执行控制台：顶部状态条、执行队列、任务矩阵与审批门同屏，信息密度高于 A。浅色与深色共用运行、等待、审批的状态语义，只反转底色和文字对比，不改变颜色含义。窄屏按运行态、等待态、审批态分层滚动，关键决定不藏进弹层。空状态集中在“没有终止运行”“无匹配文件”，并保留当前 run 的操作入口。

## C · 工作册

布局是任务工作册加可停靠证据栏：水平导航切换主会话、Worker、任务、审批与证据，右侧原生 details 默认展开上下文，窄屏时证据栏落到工作册下方。浅色为暖纸白配苔藓绿、铜色，深色为暖墨底，色相更克制。会话、产物与证据并置；空摘要明确显示“尚未生成”，说明审批阻塞，而不是伪造文件。

## 共同边界与取舍

三者的数据边界一致：样例为本地；后端前缀 `/api/v1`；票据公开投影没有依赖边与任务子 run 映射；手动 Resume 和服务端队列管理没有端点。因此依赖、风险、费用、时长只能标为未知或合成。取舍上，A 阅读性最好、操作密度最低；B 执行态最清楚、认知负担最高；C 在会话与证据之间最平衡，但需要更多横向空间。小屏优先保留主会话与审批，次要信息顺序下移。




## 初评记录

初评曾建议选择 B 作为 UI V3 的信息架构。首屏同时提供主会话、Worker 运行状态、依赖阻塞与待审批入口，用户可以直接从当前任务定位控制和证据。保持一个指令输入区，Worker 视图围绕状态、任务和执行记录设计。待审批入口在三案首屏都可到达，决定后同步请求、计数与任务状态，执行结果仍需另行回执。

A 的会话搜索、阅读宽度和 Inspector 适合高频切换。C 的审批页更易阅读，证据与产物的关系也更直接。B 的早期评审得到 19/40，A 与 C 各 24/40，主要差距集中在重复计数、术语层级和细节过早暴露。若选 B，正式设计把原始事件码和运行参数移入按需展开区，将 C 的证据和审批层次用于详情，并借用 A 的会话导航。先取得视觉方向确认，再收敛主题、组件规格和正式入口。

## V3-1 复验

- DSH 完成三套方向的界面、样式和本节之前的设计对照，按回执修复 A 深色按钮对比及移动输入区。Codex 接入原型共用的交互、设置和审批状态，组织两份独立评审与浏览器复验。
- Windows Playwright Chromium 复用项目 ui_browser。最终 43 项通过，15.78 秒。36 项覆盖三方向 × 深浅主题 × 1440×900、1920×1080、1024×768、768×1024、430×932、390×844。其余 7 项覆盖设置搜索及焦点返回、草稿、任务和文件切换、审批回执、取消对象、A 会话范围及 B 移动键盘与模拟触控。入口和五个资源返回 HTTP 200。HTML 通过唯一 ID 与控件关联检查。
- 关键返修涉及待审批入口、决定后的计数与状态、C 停止目标、A 会话与 Inspector 归属、B 移动抽屉焦点以及局部文字对比。首轮视觉评审分数记录的是返修前原型。
- Impeccable 最终静态探测有 470 条规则记录，含重叠的正文和交互字号提示。内置 URL 探测的浏览器进程启动失败，渲染证据来自 Playwright Chromium 与 Edge。正式视觉验收仍需收敛信息密度、文字规格与触控区域，并复核全部状态。
- 本机截图在 temp/ui-v3/screenshots/，静态探测回执在 temp/ui-v3/final-detector.json。验证范围为运行中的合成原型。真实 API 接入、真实 Agent E2E 和发布验收在后续阶段。
