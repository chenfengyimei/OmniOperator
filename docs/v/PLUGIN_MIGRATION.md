# V2 业务插件化迁移

迁移目标覆盖 V2 的业务功能、工具提供者和平台入口。内核继续维护执行、授权、事务、预算、回执和恢复，业务模块通过类型化安装器提供服务、路由、工具及回合提供者。已安装的插件按现行授权使用。V1 兼容入口继续走原有运行时。功能入口与调用方查 [功能地图](index/FEATURES.md)，运行验证和下一批查 [开发台账](STATUS.md)。

## 模块盘点与实施顺序

| 批次 | 覆盖范围 | 完成条件 |
|---|---|---|
| 已登记的业务功能 | Android、媒体、调度、QQ、B 站、桌面 | API、工具、服务与生命周期从功能目录装配。已有专项可从台账回查 |
| 登记工具与提供者 | 工作区文件、浏览器、会话检索、模型传输、渠道传输、平台端口 | 保留现有能力及提供者入口。随业务变更核对工具顺序、端口替换和关闭归属 |
| 技能与外部能力 | 文本技能、可执行插件、MCP | 保留技能运行报告和后台复盘。回合工具、撤权检查、未知动作复核与宿主回收共用登记的服务 |
| 投递与终端 | 持久投递、动作核查、终端、终端核查 | 迁移现有 API 与工作台入口。保留待审、复核、租约、已派发未知结果与关停责任 |
| 内容、记忆与视觉 | 来源文档、人物与人格、记忆整理、后台学习、反思、视觉与图像、维护任务 | 将各自服务和拥有的工具接入功能声明。核对来源擦除、记忆撤销、回合编排、媒体依赖和后台停机 |
| 配置、凭据与运维 | 模型与路由配置、凭据、运维审计、诊断、调试和保留报告 | 实例级路由显式登记并使用所有者鉴权。核对配置修订、凭据隔离、只读诊断和后台任务回收 |
| CLI 的部署和维护 | 安装、平台服务、发布、交换、诊断、保留计划、对象和索引维护、备份、恢复、向量配置 | 使用 `CommandPlugin` 声明参数及执行入口。保留原有帮助、审批参数、退出码、独占锁和平台回执 |
| 共享基础与兼容 | Agent 内核、提示词与上下文、原子文件和对象存储、V2 数据库与迁移、V1 运行时、V1 社区插件、独立 omni-qq、开发索引 | 保持已有基础职责、允许依赖和兼容入口，供前述模块共用 |

## 开发与验收

1. 从 [功能目录](../../agent/src/omni/composition/features/catalog.py) 和 [CLI 命令目录](../../agent/src/omni/composition/commands/) 核对真实调用方。在同一批登记服务、输入入口、权限绑定和资源归属。
2. 复用统一的所有者鉴权。额外的历史路径由业务功能声明并检查冲突。已有 OAuth 回调继续使用单次状态和现行回调边界。
3. 核对实际 OpenAPI、既有路由匹配、工具名称与顺序、状态回执以及数据修订。服务启动失败时验证可回收，涉及写入时专项覆盖撤权和未知结果。
4. 记录被测源码、专项范围与未覆盖部分。每批通过后更新台账和索引，核对 Gitee 与 GitHub 的 `v2` 回读。所有批次收口后冻结一个候选，整合运行一次离线全量。

开发时以 [能力插件合同](reference/CAPABILITY_PLUGINS.md) 和 [交接入口](HANDOFF.md) 查代码。真机、真实账号和正式发布验收沿用开发台账中的独立任务。
