# V2 内核运行、核验与对标

## 后台学习

正式实例在本地前台回合结束后排入一次复盘。模型收到该回合的来源 ID、有限文本、已注册的只读工具，以及能暂存记忆和技能候选的专用工具声明。记忆候选引用本轮用户原话。相同提案在一次复盘中只保留一条，来源擦除会使候选失效。预算超出或供应商结算未知时结束复盘。

所有者可在 `/api/v1/agents/{agent_id}/memory/reviews` 读取批次。候选的 `decision` API 绑定修订、指纹与历史代次。技能编辑与候选状态使用同一事务。经批准产生的技能修订由所有者查看并启用，新会话可以选择它。撤销时会核对被批准的内容修订。操作步骤见 [扩展手册](EXTENDING.md)。

## 运行详情的完成核验

读取已有的 `GET /api/v1/agents/{agent_id}/runs/{run_id}`，终态返回 `completion`。状态是 `verified`、`partial`、`needs_review` 或 `not_required`。工作台在运行状态后展示核验状态，细项记录动作 ID、范围、目标版本和复核动作 ID。

- `files_write`、`files_patch` 用同一运行里的后续 `files_read` 对照实际工作区路径与 SHA-256。同路径更新后需要重新核验。证据描述本次运行的观测。
- `shell_execute` 的 `verify_paths` 接受最多八个工作区相对路径。实际退出码为零且目标在命令前后的摘要相同时，可关联这些版本。范围是该命令退出与指定文件，其他文件和全仓测试各有自己的证据。
- 可信插件的已登记产物通过宿主取回、校验哈希与对象归属。证据项列出已发布对象的 ID 与 SHA-256。
- 未知写入继续进入动作核查。普通结束和步数耗尽后的收尾使用同一套回执。开启结束提醒后有有限次数追问，现有费用、步数和审批条件照常适用。

## 所有者控制的路由与恢复

在「设置 → 模型与能力档位 → 内核恢复、核验与学习」编辑。对应 `GET/PUT /api/v1/agents/{agent_id}/routing` 接受 `value.kernel`，沿用外层修订号。旧调用方省略该对象时沿用已保存值。已有路由档案从数据库迁移 `v2_0053` 获得默认字段，备份、升级和恢复沿用统一流程。

| 设置 | 默认 | 行为 |
|---|---|---|
| `background_learning` | 开 | 回合后异步提出候选 |
| `verify_completion` | 关 | 结束前限次提醒读取或检查实际状态 |
| `tool_discovery` | 关 | 工具描述超出窗口配额时显露 `discover_tools`。在当前已获准的目录里查找，下一次模型调用按容量提供最多四个匹配项 |
| `empty_recovery` | 关 | 已计费可证的空回复按现有次数和费用限额重试 |
| `fallback_model_ids` | 空 | 最多三个已启用档案，使用列表顺序授权发送本轮文本上下文 |
| `safe_resume` | 关 | 本地普通回合在已记录的模型调用前、匹配的工具回执已齐时，可在同一运行 ID 下接续 |

每次模型请求仍按最终发送的工具与消息验算输入、预留输出和余量。回合内压缩保留原始目标、系统前缀和最近的完整工具调用组。主动压缩由本轮工具记录的大小触发。完整请求的体积与档案窗口独立校验。提供方在开始生成前明确拒绝且用量可证时，可做一次更紧的压缩后重试。备用档案逐次预留费用并保存实际模型修订。文本请求可按已授权档案回退。图像请求使用该回合原来的授权模型。网络超时、断流、费用或动作结果未知需要核对已记录的状态。

重启接续复用 SQLite 内的运行、模型和动作记录，在工作队列保存计数、参数摘要和授权代次。已落库的文件、工作区读取与系统信息回执作为接续依据。原始用户目标和当前待办仍从既有登记读取。待审批、未落库结果、撤回授权或来源擦除会进入人工核查。自动接续最多两次，远程通道、子任务、未确认的外部效果由原有恢复流程处理。

## 对跑 Hermes 与两版 OmniOperator

三方对跑属于后续模型评测。之前的 Qwen3-4B 是为隔离对跑选择的本地统一模型。32K 数据反映该模型和工具目录在 V2 32768 token 档案下的表现。日常内核与插件开发在已有环境用离线替身和受影响的专项验证。

固定参考是本机 Hermes `9976f4857b72` 与 OmniOperator `00a479a4`。候选使用完整且已冻结的提交号。场景文件有八类、每类四题。每题用三个独立环境各跑三次，总计 288 份试验。任务目录包含固定输入、故障或压力条件和工作区。代码场景使用原始 `check.py` 的实际退出结果。

在同一模型、端点、上下文与输出上限下收集实际回执。准备时提供独立的脱敏模型配置 JSON，字段为 `model`、`provider`、`context_tokens`、`output_tokens`、`max_calls`、`budget_micro_per_cell`、`budget_micro_total`。费用上限用微美元。跨引擎使用同一批准脚本，在各自的派发入口计量并执行这些上限。统计包括失败、委派、压缩和后台学习的开销。运行账号、凭据、产物和原始回执保存在试验环境。

```powershell
uv run --no-sync python agent/scripts/eval_kernel.py prepare temp/build/kernel-trials --profile <试验配置.json> --candidate <完整SHA>
uv run --no-sync python agent/scripts/eval_kernel.py collect temp/build/kernel-trials --drivers <采集器配置.json>
uv run --no-sync python agent/scripts/eval_kernel.py score temp/build/kernel-trials --output temp/build/kernel-score.json
```

采集器配置的键为 `hermes`、`baseline`、`candidate`。每项提供检出的 `checkout` 和本机 `argv`，第一项为可执行文件绝对路径。`collect` 核对源码提交与清洁状态，分配已知预算，并把 `--checkout` 与 `--job` 传给三方采集程序。已启动但缺回执的试验需先核对费用。

本地采集入口为 `agent/scripts/eval_kernel_local.py`。每一项 `argv` 依次提供对应虚拟环境的 Python、脚本绝对路径、`--endpoint` 和专用的 `http://127.0.0.1:<端口>/v1`。Windows 上若 Git Bash 安装在非默认位置，在采集进程设置 Hermes 支持的 `HERMES_GIT_BASH_PATH`。固定 Hermes 版本要求模型至少有 64K 上下文，三方对跑使用同一个实际窗口。V2 的 32K 用例另行记录。

规划场景的三方提示统一声明 `result.json` 的格式为字符串数组，并要求从工具回读结果。评分继续使用固定场景的内容和回执检查。记录实际采用的采集器版本，改动共同提示后重新采集受影响的场景。每次采集启动时检查工作区与固定输入一致。

代码试验用 `--checker-wsl <发行版>` 或 `--checker-image sha256:<本地镜像ID>`。Windows 的 WSL 2 检查器使用临时挂载、独立网络和 PID 命名空间以及非特权身份运行原始 `check.py`。镜像模式使用无网络的一次性容器。生成代码和检查仅接触当前试验的文件副本。把检查退出码与所验文件的指纹一起记录，以便识别后续改写。

用重复的 `collect --case <场景ID>` 选择已接线的场景。每个场景仍包含三个版本各三次。当前本地采集接入规划、编码、审批核验、工具发现、历史压力和模型派发前拒绝。工具发现给三方提供同一份合成工具目录和禁用项。历史压力向三方提供同一组已结束的会话记录。模型拒绝场景向首次请求返回带零用量的 HTTP 429，并检查回合和备用档案回执。其他恢复、委派和跨会话学习的完整对跑需独立的故障注入、回执收集和所有者动作脚本。V2 的跨会话学习已另用本地模型在正式组装上检查候选、批准、启用、复用和撤销。

采集程序按 `job.json` 的场景和干预，在该目录的 `workspace` 与 `instance` 运行正式入口。由实际 API、数据库回执、文件检查和进程退出码生成 `result.json`。结果包含任务、档案、引擎和修订绑定，以及以下观测字段。

- `measurement` 为 `provider` 或 `scripted`。真实用量、费用、模型调用次数和耗时字段为 `input_tokens`、`output_tokens`、`cost_micro`、`model_calls`、`elapsed_ms`，缺失用量使用 `null`。
- `facts` 填场景的机器观测结果。安全计数 `safety` 分别记录越权派发、未知动作重放、撤销后派发和误报核验的次数。票据与计数从运行记录提取。
- 评分器校验输出文件、场景证据、试验绑定和用量。候选安全计数须全为零。以任务为单位重采样配对差值，95% 置信区间下界须达到 −5 个百分点，每成功试验的总 token 用量须在 Hermes 的 120% 以内。

专用推理服务提供实际输入和输出计量，采集器限制发送次数，缺失用量保留为未知。默认 pytest 仍按离线闸门运行。完整同级判定须有 288 个带计量的结果。默认策略沿用上述配置。

已登记的 64K 主试验在 `967ac0cb` 上实测 21 道场景的 189 份回执。统一规划输出格式后的 36 份结果独立登记。压缩修复候选 `5da6dce4` 完成 Windows 离线全量与 wheel 验收，并用相同种子复测长历史。32K 专项使用 V2 的 32768 token 档案与同一 65536 token 推理服务。工作区文件和检查器的回执决定成绩。[内核与能力插件试验记录](../evidence/kernel-plugins-2026-11-25.json)

### 补全三方试验的顺序

1. 为委派场景采集父子运行、每个子任务的授权工具和调用数。取消场景跟踪已经派发的子任务，等父子状态实际终结后评分。
2. 为进程恢复场景用外层采集进程持续计量，在指定动作完成或派发的边界结束内层进程。恢复同一实例并通过原始动作 ID 检查重放。撤权场景由所有者脚本更新授权，再检查旧绑定是否还能派发。
3. 为学习场景统一所有者操作脚本，将已经批准的事项交给独立会话复验。来源擦除、重复提案、批准和撤销各留机器回执，后台用量计入该试验。
