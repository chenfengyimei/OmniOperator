# 人格（PERSONA.md）

## 0. 一句话定位

人格 = `config.yaml` 里 `persona` 段的两个键（`name` / `system_prompt`），
`system_prompt` 每轮都进系统提示词。**它是"她是谁"的唯一来源**——
所以它既不能被悄悄清空，也不能被写成放凭据的地方。

本文件讲三件事：**保存契约**（什么样的正文允许保存）、**热生效**（改了什么时候起作用）、
**凭据拒绝**（为什么人设里不许放密钥）。

## 1. 配置形态

```yaml
persona:
  name: "小鱼"                 # 显示名：CLI 标题、会话元数据
  system_prompt: |             # 正文：每轮进系统提示词
    你是小鱼，一个运行在用户电脑上的个人智能体。
    说话简洁，先给结论再给理由。
```

- `name`：只用于**显示**（会话列表、CLI 标题），不进提示词。
- `system_prompt`：进提示词。`{now}` 会被替换成"见本轮运行上下文的 observed_at"
  （见 `core/context.py:42` 的 `system_prompt()`）。

## 2. 保存契约

判定实现在 `agent/src/omni/system/persona_rules.py`，入口在
`agent/src/omni/system/config_io.py:apply_updates`——**改文件之前**校验，
拒绝了磁盘上一个字节都不会动。

| 规则 | 阈值 | 违反时的文案 |
|---|---|---|
| 名字非空 | ≤ 30 字 | 「它叫什么」不能空着 / 名字太长了（N 字，上限 30 字） |
| 正文非空 | > 0 字 | 人格正文不能是空的：想换回默认人设，请把默认内容贴回去再保存 |
| 正文里没有凭据 | 命中即拒 | 人格正文里出现了疑似〈类别〉：人设会跟着每次对话进入提示词，凭据不能写在这里。请删掉这一段再保存 |
| 正文够长 | ≥ 20 字 | 人格正文太短了（N 字，至少 20 字）：这么短的内容说明身份、说话方式或规则都没写全 |
| 正文不太长 | ≤ 20000 字 | 人格正文太长了（N 字，上限 20000 字） |

**判定顺序是 空 → 凭据 → 长度**，这是刻意的：一段 16 字的正文里藏着密码时，
报"太短"会误导用户——他会去补字，而不是删掉凭据。凭据才是更危险的那件事。

### 2.1 为什么空正文一律拒绝（不区分"清空"与"不存在"）

`config_io` 对 multiline 键只校验"是不是字符串列表"，空列表 `[]` 照样通过，
于是 `_replace_multiline_block` 会把整块正文替换成空——**用户保存后人格凭空消失，
而前端还在提示「已保存」**。

这个坑来自参考项目 `xuexi/surfcore` 的一则真实事故（`docs/cases/2026-10-31-persona-tone-overwrites-core.md`）：
他们做多层人格，"保存全部"时服务端少返回一层，客户端把空值也发过去，
于是语气层的内容写进了核心文件、或者核心被清空。抄的是**判定逻辑**：
空值语义必须显式、每层一个显式分支、核心内容有最小长度闸门。

我们只有一层，但同一个洞照样存在。想换回默认人设，请把默认内容贴回去再保存——
**不提供"清空"这个动作**，因为清空和误操作在协议里长得一模一样。

### 2.2 凭据检测在 `system/text_guard.py`（单一真源）

人格与长期记忆**共用同一份检测表**（`agent/src/omni/system/text_guard.py`）。
第一版两边各写一份正则表，结果人格侧漏掉了「密码是」与 Cookie 两类——
**两份真源必然漂移，漂移只会往"某一处更宽松"的方向走**。
现在两边只共用"检测"，各自决定"命中之后怎么办"（人格拒绝保存，记忆拒绝写入）。

## 3. 热生效

`system_prompt` **在进程启动时被读进 `runtime.config`**，运行中的 Agent 用的是那份快照。
所以改了人格要**重启才生效**——工作台会显示「待重启」。

> 以前 persona 不在"改了要重启"的比较范围里：改完前端显示"已生效"，
> 但运行中的 Agent 用的还是启动时的快照——**用户以为改了，其实没改**。
> 现在人格单独参与比较（只比 `system_prompt`；`name` 只用于显示，
> 而且 bootstrap 会用目录 profile 覆盖它，整段比较会让非默认 profile 永远误报）。

## 4. 边界与已知限制

- **正文里的凭据按形态判定，不按语义**：私钥、API key、Cookie、密码赋值等确定形态才拦；
  银行卡这类**必须旁边出现上下文词**（"卡号"）才拦——Luhn 校验对 13~19 位随机数字
  通过率 9.96%，加常见 BIN 前缀后仍有 1.82%，这个误伤率不够低。
- **身份证的判定规则已升级（D36）**：现在**裸值也能拦**（不要求上下文词），
  判据是 GB 11643 校验位 + 行政区划 + 真实出生日期三条件同时成立。
  实测误伤率 0.0023%（40 万随机样本）/ 0 命中（仓库 148 个真实长数字串）——
  比"按位数判定"精确约 4000 倍，所以敢放宽。详见 §6。
- **场景层只有群聊/私聊两档（D36）**：参考项目有 core/tone/scene/daily 四层，
  我们只加了 core + 一层「场景层」（群聊/私聊各一段），没有 tone 与 daily。
  这两层的**前提**是它有一整套「人格卡编辑 + 备份 + 回档」的产品形态，
  我们只有 `config.yaml` 里的一个正文，加两层只会让保存契约变复杂。
- **改过的正文不会自动备份**：配置写入本身有 FileLock + 原子写，
  运行数据另有 `omni.system.backup` 统一入口；没有单独的"人格备份目录"。

## 5. 场景层（D36）

```yaml
persona:
  name: "小鱼"
  system_prompt: |             # 核心层：底座，每轮都进提示词
    你是小鱼，一个运行在用户电脑上的个人智能体。
  group_prompt: |              # 群聊场景层（可选，留空 = 没有这一层）
    群里说话简短些，不要抢话；一次只回一句。
  private_prompt: |            # 私聊场景层（可选，留空 = 没有这一层）
    私聊里可以展开讲，必要时给完整步骤。
```

抄的是参考项目 `xuexi/surfcore` 的 `docs/cases/2026-10-31-persona-layers.md`
与 `2026-10-31-group-tiers-tone.md` 的**判定逻辑**，四条纪律：

| 纪律 | 我们的实现 |
|---|---|
| 核心层是底座，场景层为空时行为与旧版一致 | 场景层留空 → 提示词与旧版**逐字节相同** |
| 每层一个显式分支，不给未知场景兜底 | 只有 `group_prompt` / `private_prompt` 两个明确字段 |
| 注入顺序固定：核心 → 场景 | `core/context.py:system_prompt()` 按此顺序拼 |
| 场景层只**追加**，不改写核心 | 场景层永远排在核心之后，不覆盖核心内容 |

**场景层与「注入哪些个人资料」是两件事**（正交，不是同义）：

| | 管什么 | 判定 |
|---|---|---|
| `include_personal` | 注入哪些个人资料（档案、常驻、人物卡） | 群聊一律不注入 |
| `is_group` | 用哪个人格场景层 | 群聊用 `group_prompt`，否则用 `private_prompt` |

所以**非所有者的私聊**是「有个人上下文、但属于私聊场景」——
它拿到 `private_prompt`，不是 `group_prompt`。

**保存契约与核心层不同**：场景层**空是合法的**（表示"没有这一层"），
核心层空则一律拒绝。差别在于——核心层清空会让人设凭空消失，
而场景层清空只是回到"没有场景层"的状态，两种情况行为完全一样，不存在二义。
场景层的其余规则与核心层一致：含凭据拒绝、10~4000 字。

**生效时机与核心层相同**：改了要重启才生效（工作台会显示「待重启」）。

## 6. 身份证为什么现在能拦裸值（D36）

D34 留下的限制是「裸身份证/银行卡号不拦（按位数判定会误伤订单号与时间戳，取误伤更少）」。
核实后把它拆成两半，各按各的证据处理：

**身份证：可以裸拦。** 判据不是位数，而是三个条件同时成立——
GB 11643 校验位自洽、前 6 位行政区划像真的、第 7~14 位出生日期真实存在。
实测误伤率：

| 场景 | 误伤率 |
|---|---|
| 纯随机 18 位数字 | 0.0023% |
| 日期前缀的订单号（20260801 + 10 位流水） | 0.0128% |
| 13 位毫秒时间戳 | 0% |
| 仓库 148 个真实长数字串 | 0 命中 |

对比：只按校验位判（不加省码与日期）是 9.05%——**所以三条件缺一不可**。

**银行卡：仍然不裸拦。** Luhn 校验对 13~19 位随机数字通过率 9.96%，
加常见 BIN 前缀后仍有 1.82%。这个量级会误伤真实订单号，不值得。

上下文词路径**两条都保留**：即使校验位不对（涂改、境外、旧版格式），
只要自称是身份证/银行卡照样拦——那句话本身就是高置信信号。
