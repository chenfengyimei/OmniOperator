## 一、本会话做了什么（三个阶段）

### 阶段 1：SeekMemory 仓库只读审查（未改任何代码）

- 克隆 https://github.com/NeverENG/SeekMemory 到临时目录逐行审查（25.6k 行非测试
  代码 + 5 份基准报告 + CI + 提交历史），临时目录用完即弃，不涉本仓库。
- 结论：机制真实、工程纪律好（130 测试文件、分层强制、自评报告敢写自己的 0 贡献）；
  但对外宣称的"省 32% token"在仓库里**找不到可复现出处**（全库 grep 仅命中
  消融报告里的"噪声 32%"，与 token 无关）；"更有活人味"是同模型自评、单次采样，
  只能当趋势。仓库实测数字：vs 全量注入注入字符 245×、vs keyword 基线贵 6% 但
  命中 +11.7pp、证据闸门使 prompt token −29%。
- 可取之处（本项目视角）：命中强化+冷却防"越提越重要"、元记忆（区分"已忘"与
  "没说过"）、召回带相对时间、成本从热路径拿走（写侧离线 + 读侧零模型调用）。

### 阶段 2：最小融入三件套（提交 `cb29b76`，8 文件 +374/−21）

全部在现有 `facts`/`tombstones` 结构上实现，**不新增表、不新增依赖、不加衰减**：

1. **命中强化 + 冷却**：`facts` 新增 `hits`/`last_used`（schema + `_migrate_columns`
   两条路齐，旧库自动补列）；`touch_facts` 原子条件更新：30 分钟冷却 + 每天最多
   一次。强化**只参与重排、不做入场券**：检索链（FTS bm25 → 全词 AND → 全词 OR
   → 中文 2-gram）仍是唯一候选来源，增益 `0.15 × cap 10 = 1.5` 个链位，hits=0 时
   顺序与纯链序完全一致。
2. **元记忆**：recall 无命中且私聊时，`forgotten_matches` 查遗忘墓碑，回复区分
   "说过但被要求忘掉"与"没说过"；群聊不给墓碑线索（防跨人泄露）。
3. **相对时间**：召回行带"（N 天前记住的）"口语化时间线索（`humanize_age`，
   解析失败安静降级）。

连带修正：recall 从 `read_only=True` 改为"SAFE 但记账写状态"（read_only 的语义是
批内并发资格，写状态工具标它是撒谎）——保持串行，不进批内并发池。

### 阶段 3：记忆系统全面核实 + 三项修正（提交 `d100177`，5 文件 +104/−6）

核实结论（对 cb29b76 与整个记忆系统）：

- **数据结构完整**：facts/tombstones/summaries 契约闭环（墓碑挡写入、挡再学习、
  遗忘使摘要失效）；hits/last_used 新库与旧库两路迁移齐。
- **上下文组装无冗余注入**：进 prompt 的只有 persona、回合快照（resident+profile+
  人物卡，带"变了才重发"的去重协议）、摘要+未覆盖消息；`dialogue`/`session_log`/
  `journal`/`people` 是档案层、docstring 明确"不进上下文"。**不存在"多余记忆模块
  污染上下文"的问题**，无需重构、无需合并模块。

抓到并修复的三个真实缺陷：

1. **后台召回给 hits 注水**：review（回合后）与 journal（夜间整理）两个后台
   worker 的注册表也注册了带记账的 recall，夜间取材每查一次命中事实 +1 hits，
   排序强化信号会被污染成"整理模型爱查什么"。修复：`register_memory_tools` 新增
   `count_hits: bool = True` 参数，bootstrap 两个后台注册表传 `False`。
2. **forget 作用域不对称**：remember/recall 跟随 run 作用域，forget 硬编码搜
   private——群聊事实"记得住、召得回、永远忘不掉"，且群聊一句"忘掉 X"会去搜并
   **删除私人事实**（跨作用域删除事故）。修复：forget 检索作用域跟随当前 run。
3. **删旧事实静默失败**：forget 借 `fact_rows(500)`（工作台展示口径，按新到旧截
   500 条）反查 id——库超 500 条后删旧事实报"没有找到"。修复：新增
   `MemoryStore.fact_ids_by_contents`（SQL IN 全库精确匹配，不看条数）。

## 四、后续还差什么（按优先级）

1. **真实验收（最重要）**：全部验证都是离线/模拟，真实模型下的效果未测——
   后台 worker 实际会不会频繁调 recall、hits 强化在真实对话里的排序体感、
   群聊 forget 走 CONFIRM 审批流的体验、相对时间线索对模型复述的帮助。
   **均未验证，不得记"完成"**。
2. **工作台记忆页 UI**：`fact_rows` 已返回 hits/last_used，但工作台记忆页尚未
   展示这两个字段（人看不到"这条为什么排前面"）。
3. **count_hits=False 的 bootstrap 接线无自动化测试**（组装根策略，tests 不构造
   bootstrap）；目前只靠 tools 层单测保证参数行为正确。排查会话可人工核对
   bootstrap.py 中 `_review_registry` / `_journal_registry` 是否仍传 `count_hits=False`。
4. **embedding 混合检索路径的强化融合未验收**：`HybridMemory.search` 的 lexical
   输入序已含强化重排，RRF 融合后的实际效果没人看过。
5. **远期（借鉴自 SeekMemory 但刻意没做的）**：公开数据集（LoCoMo/LongMemEval
   子集）上的对外可比跑分；四层沉淀/艾宾浩斯衰减与本项目"遗忘只有显式墓碑、
   事实不衰减"的设计冲突，**刻意不搬**，除非先推翻该设计决定。

## 五、隐患清单（排查会话重点看）

- **多会话协作的批量提交风险（已发生两次模式）**：并行会话批量 add/commit 会把
  别的会话改到一半的文件卷进去（本次 93890de 卷走 bootstrap+台账；更早 cb29b76
  之前 web_static 46 个文件卷入事故）。**任何提交前必须
  `git diff --cached --name-only` 逐文件核对 + grep web_static 自检为 0**。
- **tombstone 无 scope 列（既有语义）**：群聊 forget 会建全局墓碑，挡掉所有
  作用域对该内容的再写入。这是"遗忘只有显式墓碑"设计的既有取舍，不是本次引入，
  但群聊 forget 打开后触发面变大，值得排查会话复核一次。
- **forget 检索 limit=8**：模糊命中超 8 条且精确匹配排 9 名以后时，forget 仍报
  "没有找到"（既有限制，强化重排可能轻微改变边界情况下的排序）。工具文案已引导
  用户给完整句子；若排查发现真实误报，可考虑 forget 先精确反查再模糊搜索。
- **recall 每次召回 3 次库操作**（search + touch + timestamps）：SQLite 单机场景
  可接受，若未来记忆量上万或迁远程库需合并为一次往返。
- **hits/last_used 的时间比较靠 ISO 字符串字典序**：跨时区偏移变化（DST 等）有
  边界误差，对启发式排序信号可接受（代码注释已声明）。
- **SeekMemory"省 32% token"未采信**：出处不可复现，本项目文档中**没有**引用
  该数字；排查会话若在别处看到该声明，不要当成有依据的结论。
