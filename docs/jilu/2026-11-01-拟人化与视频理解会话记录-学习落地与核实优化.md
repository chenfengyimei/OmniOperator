### 1. 真机验收脚本（新 `agent/scripts/manual_d36_acceptance.py`，需 `--run`）

  这比"调用→被拒→改写"更严格。另做**闸门直测**（`MemoryGuard.check`）确认即使

  名单内正常处理（证明闸门没把所有人都拦掉）；主动私聊被安静时段闸门拦时的
  文案实测为「错误：安静时段，等待下一次补投。……不要另发私聊。」。

### 2. 身份证裸值可拦（`system/text_guard.py`，策略版本 v1 → v2）

D34 的取舍是「按位数判定会误伤订单号与时间戳，取误伤更少」。核实后发现：
**位数是错的判据，校验位才是对的**。改成 GB 11643 校验位 + 行政区划 +
真实出生日期三条件同时成立：

| 判据 | 随机 18 位误伤率 |
|---|---|
| 只按位数 | 100% |
| 只按校验位 | 9.05% |
| 校验位 + 省码 + 真实生日 | **0.0023%** |

仓库 148 个真实长数字串 **0 命中**；日期前缀订单号 0.0128%；13 位毫秒时间戳 0%。

**银行卡维持不裸拦**：Luhn 对 13~19 位随机数字通过率 9.96%，加常见 BIN 前缀后
仍有 1.82%——这个量级会误伤真实订单号。上下文词路径两条都保留。

### 5. 活跃时段建议安静时段（新 `safety/activity.py`）

**核实**：surfcore 的「生物钟窗口」是**用户手动配置的固定窗口**
（`plugins/surfcore/lib/scheduler.js` 的 `cfg.night.windows` + 设置页的
「作息窗口编辑器」），**不是从数据里学出来的**——所以「学作息」我们并不落后于它。
差异在形态：它管「什么时候叫醒 B 站鲸鱼」，我们管「什么时候别主动打扰用户」。

落地要点：按**天**统计（一条长谈不该把某个小时拉满）、只统计 `role='user'`
（assistant 的消息是我们自己回的，用户凌晨收到回复不代表他凌晨还醒着）、
找最长连续静默区间（跨零点算连续）、全天静默占比 >75% 时不给建议。

**只给建议、不自动生效**：推导结果不写 config.yaml、不改任何闸门行为，
只作为 `/api/memory-system/overview` 的 `activity.suggestion` 呈现。

## 三、明确**不做**的（及理由）

| 项 | 理由 |
|---|---|
| 对话收尾/潜水（信号打分） | 它的六信号收尾判据建立在**有状态对话**（模型知道这句话是结尾）之上。我们是一问一答、每次调用都是新回合，没有"这句话是不是结尾"这个可观测量。抄它会得到一个永远判不出"该收尾"的状态机——没人调、没人敢删的死代码。**要退一步做**是通道层的冷却位，但我们已有 `merge_window_s`（合并窗口）在做同一件事，不重复造。 |
| 银行卡裸值拦截 | Luhn 误伤率 1.82%，不够低。 |
| 记忆容量自动合并 | 破坏出处锚点的可回查链。 |
| 自动改安静时段 | 猜错方向如果是"拦多了"，用户会以为系统坏了。 |
| surfcore 的八项（鱼群保护/桌宠/DSH 形态/置信度状态机/群分层/回合内可见性/1-100 重要度） | 每一条都能说清为什么在我们的形态里不成立。抄一个前提不成立的机制比不抄更糟——它会变成没人调、没人敢删的死代码。 |

### 4.2 工程隐患（多会话协作相关，**这是本会话最大的坑**）

#### 隐患 A：工作区被并行会话改到一半 → 本地跑不起来

本会话开始时，主工作区的 `memory/state_schema.py` 处于**并行会话改到一半**的状态：
HEAD 有 `_SCHEMA_V15`，工作区把它删了但 `config.STATE_SCHEMA_VERSION` 仍是 15
→ `StateStore` 初始化直接抛 `缺少 v15 的迁移脚本`。
**任何需要建库的操作都会失败**（包括起工作台、跑真机验收）。

- **识别方法**：`StateUnavailable: 缺少 vN 的迁移脚本`。
- **本会话的应对**：改用**隔离 worktree**（`git worktree add --detach`）开发与验收，
  主工作区一个字不动。
- **给排查会话的建议**：看到这类报错先查 `git log --oneline -3` 与
  `git status --short -- agent/src/omni/memory/state_schema.py`，确认是不是别人改到一半。

#### 隐患 B：从主工作区复制文件 ≠ 拿到「自己的版本」

**本会话实际犯了这个错并已修**：D36 实现提交里 `config.py` 与 `config_io.py`
**混进了并行会话未提交的改动**（`class Updates` / `RuntimePaths.updates` /
`('updates','channel')`）。原因是我从主工作区复制文件到隔离树再 `git add`——
工作区版本里本来就混着对方的改动。

- **正确做法**：以基线提交为底、**精确重放「只有我的改动」**写进索引
  （`git show <base>:<path>` → 精确字符串替换 + **断言恰好命中一次** → 
  `git hash-object -w` + `git update-index --cacheinfo`），**工作区一个字不动**。
- **注意**：`git hash-object -w --stdin` 默认走行尾过滤；要存原始 CRLF 用 `--no-filters`；
  用 `--path=` 会触发 clean filter 把 CRLF 转 LF → 整文件 diff。
- 新文件进索引要 `git update-index --add`。

#### 隐患 C：`git reset` 会清掉已暂存的内容

本会话为了拆分「实现提交 / 文档提交」执行了 `git reset -- <文档文件>`，
结果**把索引里其他文件也一并清空**（那些文件相对 HEAD 已提交，reset 后变成"未暂存"），
导致下一次提交变成了「反向提交」（把场景层删掉、把文档回退）。
**教训**：多会话协作下不要用 `git reset` 拆提交；要么一次提交完，
要么用「构造索引」精确控制提交树。

#### 隐患 D：MSYS 路径在 Python 里解析成别的盘

`/d/xm/omni-d36-idx` 在 Windows Python 里 `Path(...).resolve()` 得到
`D:\d\xm\omni-d36-idx`（**不存在**）→ `project_index.py` 的 `--root` 静默失效，
回退到默认 `PROJECT_ROOT`（主工作区）→ **索引里混进了并行会话的模块**。
- **给排查会话的建议**：在 Windows 上给 Python 传路径一律用 `D:\...` 形式，
  并**核对输出的模块数/文件数**是否与预期一致。

#### 隐患 E：`test_command_jobs.py` 是 flaky（与本会话无关，但会干扰排查）

`test_cancellation_and_timeout_reap_owned_process` / `test_queue_cancel_and_close_budget`
在**纯净 HEAD 树**上也会失败，且**失败参数每次不同**（`parent` / `manual` 轮换）。
本会话与并行会话各自独立复现过，结论一致：**该测试本身不稳定**，
真机跑着工作台与三个服务时负载型 flaky，单独复跑通过。
**排查时若只看到这一项失败，不必怀疑自己的改动。**

#### 隐患 F：文档契约测试会因文档改动失败

`docs/DEVELOPMENT_STATUS.md`、`docs/PERSONA.md`、`docs/MEMORY_SYSTEM.md` 有
契约测试（`test_community_docs.py` / `test_project_catalog.py`）。
本会话改文档后跑过：`71 项全绿`。**改文档后要重跑这两个文件。**

### 4.3 多会话协作的纪律（本会话验证有效）

1. **隔离 worktree 开发**：脏工作区里跑不了测试（隐患 A），且会污染别人的在途改动。
2. **提交树自校验取全量数字**：`.venv` 是 editable 安装（`.pth` 指向主工作区 `src`），
   在 worktree 里跑 pytest **加载的仍是主工作区代码**。正解：
   `git worktree add --detach <tmp> HEAD` 且 `PYTHONPATH=<worktree>/agent/src` 重跑。
   本会话用 `git write-tree` + `git commit-tree` 建临时提交树再自校验，数字最干净。
3. **`git update-ref` 一定要带旧值期望**：`git update-ref <ref> <new> <old>`。
4. **行尾**：仓库里 `docs/index/*` 的 blob 存 CRLF，源码与 `docs/*.md` 存 LF。
   提交前逐文件核对 HEAD blob 的行尾 == 索引 blob 的行尾。
5. **索引会被并行会话的提交推旧**：每次提交后按当前 HEAD 再重生成一次索引。
