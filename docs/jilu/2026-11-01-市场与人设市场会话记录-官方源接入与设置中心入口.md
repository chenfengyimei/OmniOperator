## 2. 为什么这么设计（后来者改之前先读）

1. **市场是独立只读服务，不塞进主程序。** 主程序是本地 agent，给它开一个"对外分发内容"的写入口等于把攻击面搬到自己身上。`market/server.py` 只有 GET，没有上传接口；投稿走人工审核后落 `content/`。
2. **API 契约刻意与既有 `omni/plugins/server.py` 完全一致**（`/api/plugins`、`/api/download/<id>` 带 `X-Plugin-Sha256`）。所以 `CommunityClient` 一行没改就能对接——这是"官方默认源"能成立的前提。
3. **人设导入只填表，不写配置。** 弹窗点「导入这套」只做两件事：写本机预设库（`localStorage` 键 `omni_persona_presets`，id 前缀 `market-`）+ 填进表单。真正生效仍要用户点「保存人设」。理由是：市场内容不该有"静默改运行配置"的权力。
4. **人设不做服务端存储。** 主程序侧人设只有 `config.Persona(name, system_prompt)` 两个字段，没有账号体系，存服务端只会多一份要同步的状态。市场只负责"发卡"，不负责"记你装了哪套"。
5. **构建要确定性。** zip 固定时间戳、`published_at` 首写后沿用——否则每次 `build.py` 都会让所有内容看起来"刚更新过"，指纹也会漂。删掉 `dist/` 重建后 sha256 完全一致（已验证）。

### 事实澄清（不是隐患，但会误导排查）

**根目录 `src/omni` 与 `agent/src/omni` 是同一份文件（同一 inode），不是两套代码。**
`stat -c '%i %n' src/omni/memory/state_schema.py agent/src/omni/memory/state_schema.py` 两个输出相同。所以：
- 改任一边等于改另一边，不存在"两棵树不同步"这种问题；
- 但 **`/src/` 在 `.gitignore` 里**，从根目录 `src/` 读到的就是 `agent/src/` 的内容，`git status` 只显示 `agent/...` 那条路径，容易让人以为"根目录有一份没被跟踪的旧代码"；
- 在 `market/` 等非 `agent/` 目录里跑脚本时，`omni` 会解析到根 `src/`（即同一份），配合 `uv` 的 project 解析会触发 `agent_spaces` 的目录校验报错（见 H8）——**现象像环境坏了，其实是工作目录问题**。

## 8. 本会话踩的坑（给后来者，别再踩）

### 8.1 索引共享导致混装（两次）
见 H2。最隐蔽的是第二次：以为 `GIT_INDEX_FILE=/tmp/xxx` 复制索引就隔离了，实际上**复制品里带着别人已暂存的文件**，`git commit` 照单全收。
正确做法：独立 worktree + `git update-ref`。

### 8.2 UI 测试在跟自己赛跑
`test_ui_market.py` 原本在 `locator.wait_for(state="visible")` 后直接 `inner_text` 断言。但插件分区是先渲染「正在读取…」再异步换结果——**可见不等于加载完**。本地连跑 5 次挂 2 次，报错 `assert '还没有装任何插件' in '正在读取…'`。
修法：
```python
page.wait_for_function(
    "document.querySelector('#plugin-installed')?.textContent.includes('还没有装任何插件')"
)
```
修后连跑 6 次全绿。
**通用规则：断言异步容器的文案之前，先等文案本身出现。**

### 8.3 版本串漏一个文件 = 模块被实例化两次
并行会话把全局 `?v=` 从 m17 统一升到 m19 时，我的 `hub-market.js` 没被扫到，导致它 `import` 的是 `dom.js?v=...m17`、别处 `import` 的是 m19 —— 同一个模块按两个 URL 各加载一份，`$`/`esc`/`api` 出现两套实例。已由 `d8d4929` 补齐。
**加新前端模块后，务必 `grep -rho "dom\.js?v=[0-9a-z]*" ui/app/*.js | sort | uniq -c` 查版本串是否唯一。**

### 8.4 在 `market/` 目录下跑脚本会解析到仓库根 `src/`
见 H8 与「事实澄清」。现象是 `ValueError: workspace 目录不能覆盖内部数据或控制目录`，容易被误判成"环境坏了"。

### 8.5 台账数字写错但故意没改
见 H11。因为该文件正被并行会话大改，就地改会混进别人的提交——**宁可留一条可查的记录，也不制造一次混装**。

### 8.6 "全绿"这个数字会变，别把它当常量
同一组守卫：21:30 跑是 **113 passed**，22:05 再跑是 **114 passed**（并行会话加了 1 项测试）。所以要盯的是 **failed/error = 0**，不是条数。任何引用的数字请连带时间戳一起引。

## 9. 给下一个会话的一句话

这条路（人设/插件市场）**代码已经能用了，缺的是一次真实部署和一次所有者亲手验收**。真正容易出事的不是功能，而是三件与"多会话共享"有关的事：

1. **共享 git 索引**——动 `agent/` 与 `docs/DEVELOPMENT_STATUS.md` 之前，先看 `git status --short` 里有没有别人的东西（本会话已因此混装两次、回退一次）；
2. **共享大台账**——你的条目可能被别人的批量重排挤掉，提交前 `grep` 一次自己的关键词；
3. **瞬时不可运行的工作区**——看到大面积 ERROR 先判断"这是谁的未提交改动"，而不是急着改代码（§5 H15 有实测时间线）。

判断顺序建议：先 `git status --short` 与 §6 ⓿ 的健康检查 → 再跑 ⑥⑦⑧ 定位层 → 最后才看代码。
