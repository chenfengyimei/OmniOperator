## 2. 为什么这么做（问题链）

1. **用户报障**：auto 档把「查询一下当前deepseek剩下多少余额」判为 retrieval；检索档没有查余额的工具，agent 直接回答「查不到」，**没有用 `request_mode` 升档**。
2. **根因不是能力不够，是模型不知道能升档**：升档说明此前**只存在于 `request_mode` 的工具描述一处**；而轻量档回合里模型未必把「工具不在规格里」与「我可以请求换档」联系起来。
3. **为什么写四处而不是只改文案**：模型读到的入口不止一个——系统提示（每轮固定前缀）、工具规格（每轮）、工具结果（被拒时）、以及伪造调用（不在规格里）。**只补一处等于赌模型恰好读到那处**；四处同口径才闭环。
4. **为什么拒绝文案要分两类**：升档**不改变场景许可**——群聊/他人私聊拿不到的工具，升到 agent 也拿不到。对这类拒绝提示「去升档」是**误导**（会诱导模型反复试探、消耗升档额度、让用户以为升档能解决）。所以：**档位不够 → 提示升档；场景不许可 → 保持原样**。
5. **为什么 agent 档伪造调用要兜底**：agent 档**不发**升档工具，但系统提示里写着「缺工具就调 request_mode」，模型可能据此伪造调用。原来的错误文案像故障（会诱导重试），改成友好说明后模型会直接用手头工具继续。

**H1【高】远端落后本地 40 提交。** `origin/master=2159c30` vs 本地 `HEAD=7ae23bd`（`git rev-list --left-right --count origin/master...HEAD` = `0 40`）。从 gitee 克隆会得到少了 40 提交的旧树，审计结论不可移植。

**H4【中】混合文件的提交手法。** 同一文件里既有我的改动又有对方在途内容时：`git show HEAD:<path>` 取原文 → 只打自己的补丁（断言每处命中恰好一次）→ `git hash-object -w --path` → `git update-index --cacheinfo 100644,<blob>,<path>` → 提交。工作区保留对方改动（MM 状态）。本会话 7 个文件因**编辑前均与 HEAD 一致**，可直接 `git add`。

**H5【中】档位/提示是服务端行为。** 只随**工作台进程重启**生效，浏览器刷新无效。实测前确认进程启动时间晚于提交时间（当前 pid 24664 起于 11-01 21:27）。

**H6【中】uv 同步在服务运行中会失败。** `uv run` 重建会因运行中的 `omni-web.exe` 文件锁报 `os error 32`（退出码 1）。跑测试/脚本一律用 `uv run --no-sync`；venv 是 editable 安装，`--no-sync` 仍取到源码改动。
