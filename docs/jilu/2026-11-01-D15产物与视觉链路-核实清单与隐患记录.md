## 3 隐患清单

分级：**P0** = 功能看起来做了但实际没工作 / 会误导模型；**P1** = 数据、越权、可解释性；
**P2** = 性能、维护、协作。

### H1（P0，**已复现**）工具文本过度承诺：「已作为图像内容提供给模型」

- 位置：`agent/src/omni/tools/shots.py:57-61`
- 现象：`can_view=True` 时，工具结果写「这张图已作为图像内容提供给模型，可以直接描述/分析它」。
  但 `can_view` 只是 bootstrap 阶段算出的**资格**（隐私开关 + 有视觉模型），**不代表本回合真的发了图**——
  单回合附图数上限、单图超限、产物过期、指纹不符都会让 `_attach_images` 拒发。
- 复现（本次实跑，`max_images_per_turn=1`，一次截两张）：

  ```
  工具文本声称『已提供给模型』次数: 2
  实际附图块数: 1
  同回合降级说明含『未附加』: True
  矛盾成立: True
  ```

  即：第 2 张的文本对模型说"你看得到"，紧跟着的 user 消息又说"未附加：本回合附图数已达上限"。
  模型面对两句矛盾指令，最可能的反应是**假装看过**——这正是 A13 要消灭的行为。
- 建议修法（二选一）：
  1. 工具文本不承诺结果，只说「已存为产物 `[artifact:id]`，是否随本轮发送见随后的图像说明」；
  2. 或把 `can_view` 降级为"有资格"，文案改成「将作为图像内容发送（若本轮未超上限）」。

### H2（P0）三道视觉门禁静默失败，用户零感知

- 位置：`agent/src/omni/core/agent.py` `_attach_images` 开头三个 `return`：
  `self._artifacts is None` / `not config.vision.send_to_cloud` / `vision_model is None`。
- 现象：**没有日志、没有 run 事件、工作台也没有提示**。用户配了模型、以为开了图，模型说"看不到图"，
  用户不知道该改 `send_to_cloud` 还是该给模型加 `capabilities.*.vision: true`。
- 影响：这是"能力静默失效"，比报错更难查。真实用户的第一反应会是"这功能是假的"。
- 建议：至少 `run.event("image_skipped", reason=...)` 一次；工作台在产物页签顶部显示
  「图像输入：未开启（config.yaml → vision.send_to_cloud）」的一行状态。
- 附带：`bootstrap.py:600-612` 与 `agent.py:_vision_route_model` 是**两份几乎相同的判据**。
  项目已有教训"同一判定两处用 → 必然漂移"（人格/记忆凭据正则那次）。建议抽一处共用。

### H3（P1）产物 HTTP 接口不做会话归属校验（含 DELETE）

- 位置：`agent/src/omni/channels/web_api/artifacts.py:66`（`store.get(artifact_id)` 不传 `session_id`）、
  `:79`（`store.delete(artifact_id)` 同样不校验）。
- 现状：台账明确写了"工作台图像路由不走跨会话校验（配对会话=本机所有者，刻意）"。
- 风险：模型侧防线（`get(session_id=sid)`）还在，**Web 侧等于绕过**。本机单用户可接受；
  一旦工作台被反代/共享给第二个人（`web.py` 支持 host 白名单），就是**跨会话读别人截图 + 删别人产物**。
- 建议：至少在文档与界面标注"本接口假定单用户"；若要多用户，`DELETE` 必须先补归属校验。

### H4（P1）`run._attached_image_ids` 是动态属性，`RunContext` 没有声明

- 位置：`agent.py:1396` 赋值，`agent.py:709` / `:1347` 用 `getattr(..., None)` 读；
  `core/run.py` 的 `RunContext`（第 112 行起）**没有这个字段**。
- 风险：类型检查看不到；未来若有人重构掉那行赋值，清理逻辑会静默退化成"keep 集合永远为空"，
  于是**过期清理会删掉活跃 run 还在引用的产物**——症状是长回合中途图片 404，极难定位。
- 建议：在 `RunContext` 上加 `attached_image_ids: set[str] = field(default_factory=set)`，
  读写都走字段，并在 `test_artifacts.py` 里断言"字段存在"。

### H5（P2）`cleanup()` 是 N+1 查询 + 每回合扫目录

- 位置：`memory/artifacts.py` `cleanup()`：先 `SELECT ... WHERE expires_at IS NOT NULL`，
  再对目录里**每个**合法 id 文件名单独 `SELECT 1 FROM artifacts WHERE artifact_id = ?`。
- 现状：产物上限 500MB、保留 7 天，量级通常几十到几百张，开销可忽略；
  但**每个回合结束都会跑一次**（`_sweep_artifacts`），且 `iterdir()` 在机械盘/网络盘上会明显。
- 建议：改成一次性 `SELECT artifact_id FROM artifacts` 建集合再比对；或按 `now - last_sweep` 限流
  （例如最多每 10 分钟一次）。

### H6（P1，`[推演]`）上下文压缩后图像消失，但 `_attached_image_ids` 仍记着 → 后续不再补发

- 链路：`compress.py` 把旧消息压成摘要（`_text_of` 把图像部件转成「（此处已向模型发送一张图像）」占位），
  压缩后的 messages 里**已无 image 部件**；而 `run._attached_image_ids` 仍保留这些 id。
- 推演后果：同一回合后续再次调用模型时，`_attach_images` 因 `aid in attached_ids` 跳过，
  **模型上下文里既没有图、也不会重发**，只剩一句"（此处已向模型发送一张图像）"——
  模型可能把这句当成还没看到的东西，也可能当成看过。语义模糊。
- 未实测原因：需要构造超阈值上下文 + 真实压缩，成本较高。**建议排查会话优先复现这条**。
- 建议：压缩时若某 id 的图像消息被移除，从 `attached_ids` 里删掉（允许后续按需重发），
  或把占位文案改成明确的"（图像已从上下文移除）"。

### H7（P2）目录搬迁留下的双路径 junction（`src/` → `agent/src/`、`tests/` → `agent/tests/`）

- 事实：仓库根 `src`、`tests` 是 **Windows JUNCTION**，指向 `agent/src`、`agent/tests`

### 5.2 关键设计取舍（避免排查时误判成 bug）

1. **图像块以 `role=user` 消息附加在 tool 结果之后**——OpenAI 兼容接口不接受 tool 消息里带图像部件。
   个别严格供应商拒这种形态时会整回合报错，属已记录的剩余限制，不是静默失败。
2. **`vision.send_to_cloud` 默认关**——纯本地存图 ≠ 云端上传许可。默认配置下模型"看不到图"是**设计**。
3. **产物 id 只认 8–32 位小写 hex**（`MARKER_RE` 与 `ArtifactStore.get` 共用一份正则）；
   目录里认不出的文件名**绝不删**（宁可留垃圾也不误删用户文件）。
4. **过期判定统一走 `_as_dt`**（naive 补本地时区）——naive/aware 直接比会抛 `TypeError`，
   读产物整个挂掉比"比错"更糟。`get(allow_expired=True)` 只给清理保留场景用，不是绕过过期。
5. **登记失败删已写文件，但不先登记后写**——反过来会留下"有行没文件"的鬼记录。
