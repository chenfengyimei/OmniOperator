## 三、探针实验与结论（关键：打包方案**未**验证通过）

探针目录：`C:\Users\cy\.codely-cli\tmp\webpkg-test\`（仓库外；结构 `repo/web` + `repo/agent`，内含探针版 `hatch_build.py`）

| # | 实验 | 结果 |
|---|---|---|
| 1 | `[tool.hatch.build.targets.wheel.force-include] "../../web" = "omni/web_assets"` | **失败**：hatchling 以**项目目录**（agent/）为基准解析 `..`，`../../web` 指向仓库外一层 → `FileNotFoundError: Forced include not found` |
| 2 | 改为 `"../web" = "omni/web_assets"`（纯 force-include，无钩子） | **成功**：wheel 内含 `omni/web_assets/index.html`、`omni/web_assets/ui/app.js` |
| 3 | 加自定义构建钩子 `[tool.hatch.build.hooks.custom]`（`initialize` 里按实际位置填 `build_data['force_include']`） | **失败**：wheel 里反而**没有** `web_assets`（钩子未生效，或键名/时序不对）——**未定位** |
| 4 | sdist 目标加 `force-include "../web" = "src/omni/web_assets"` | **落点错**：资源进了 sdist 根的 `omni/web_assets/`，不是 `src/omni/web_assets/` |

### 硬结论

- 「仓库根 `web/` 也能被打进 wheel」**在纯 force-include 下可行**（实验 2）。
- 但 **sdist → wheel 这条链必然断**：pip 解包 sdist 后项目根变了，`../web` 相对路径不再指向任何东西。实验 3/4 的失败说明「用构建钩子兜住两种场景」这条路**尚未走通**，需要重新设计。可考虑的方向（均未验证）：
  - sdist 里把界面放到**包内路径** `src/omni/web_assets/`，wheel 在 sdist 场景直接按包内路径收录（但当前 force-include 的目标路径语义落在 sdist 根，需确认 hatchling 对 sdist force-include 目标路径的解析规则）；
  - 或改变 sdist 构建根，让 `../web` 在两种上下文里都成立；
  - 或放弃「界面进 wheel」，改由安装器把仓库根 `web/` 复制进安装目录（会引入安装期状态，需与 `scripts/installer_lib.ps1` 联动）。
- **因此：在打包链路解决之前，不要动 `git mv`。** 先搬目录再发现 wheel 缺资源，仓库会处在「界面在包外 + wheel 不含界面」的坏中间态。

### 本次踩到的平台坑（Windows）

- PowerShell 5.1 的 `Set-Content -Encoding utf8` 会写 **UTF-8 BOM** → hatchling 用 `tomllib` 读 pyproject 直接报 `TOMLDecodeError: Invalid statement (at line 1, column 1)`，看着像 TOML 写错，其实是 BOM。
- `write_file` 工具对**已存在**文件会**保留原编码** → 想换编码必须先 `Remove-Item` 再写。
- 可靠写法：Python `Path.write_bytes(body.encode('utf-8'))`，或先删文件再用写入工具新建。
- `uv build` 需要 `UV_INDEX_URL` 指向可用镜像（本机用 `https://mirrors.aliyun.com/pypi/simple`）。
