## 二、本会话核实并修复的真实缺陷

**每一条都是实测发现的，不是推断。**

### 2.1 【最严重】`_SCHEMA_V15` 被删但 `STATE_SCHEMA_VERSION` 仍是 15

**这是本次记录时工作区的致命状态**，导致全量 **305 failed / 286 errors**。

- 现象：任何新建 `state.db` 都抛 `StateUnavailable: 缺少 v15 的迁移脚本`（`memory/state.py:158` 附近）。
  受影响的不只是 state 测试，而是**所有依赖 runtime 的测试**（web / cron / outbox / qq / usage / ui…）。
- 根因：`agent/src/omni/config.py` 的 `STATE_SCHEMA_VERSION = 15`，但工作区的
  `agent/src/omni/memory/state_schema.py` 被**纯删除 33 行**（`git diff --numstat` = `0 33`），
  把 `_SCHEMA_V15` 定义和 `MIGRATIONS[15]` 一起删了；而 `memory/usage.py` 仍在
  `INSERT/UPDATE/SELECT llm_budget_scope`——表永远建不出来。
- 处置：`git checkout -- agent/src/omni/memory/state_schema.py` 恢复（该文件工作区只有这一处删除）。
- 修复后实测：全量 **1932 passed / 3 failed / 2 errors**（442.74s），MIGRATIONS max = 15 = `STATE_SCHEMA_VERSION`。
- **给后续会话的检查命令**（一致性守卫必须常跑）：

```bash
uv run --no-sync python -c "
from omni.memory.state_schema import MIGRATIONS
from omni.config import STATE_SCHEMA_VERSION
assert max(MIGRATIONS) == STATE_SCHEMA_VERSION, f'版本不一致: {max(MIGRATIONS)} vs {STATE_SCHEMA_VERSION}'
print('OK', STATE_SCHEMA_VERSION)"
```

> ⚠️ **这类事故会重复发生**：`STATE_SCHEMA_VERSION` 在 `config.py`、迁移脚本在 `state_schema.py`，
> 分居两个文件。**建议**（未做）：在 `state.py` 加一条启动期断言，或把它写成
> `STATE_SCHEMA_VERSION = max(MIGRATIONS)` 的派生值。见 §4.3 待办。

### 2.2 5 处测试函数被静默覆盖（`9a7d6ef`）

同文件同名 `def test_xxx` 定义两次，后者覆盖前者，**前一个测试从未运行过**。
`scripts/scan_duplicates.py` 扫出 5 处（test_memory / test_web / test_web_model_key ×3），
全是并行会话各写一版同名测试的合并残留。已去重并让被吞的测试真正执行；
新增 `test_no_duplicates.py` 把检查接入 pytest（`test_arch.py` 原来只扫 `src/omni`，**tests/ 无人守**）。

### 2.3 终端回显测试的间歇失败（`01e9625`）

`test_terminal_session_echo_roundtrip` 在全量并行下间歇失败。根因：`_read_until` 用
「读 400 次」作预算，但 `winpty.read` 空读立即返回，PowerShell 启动慢时预算被瞬间烧光。
改为 **20 秒墙钟截止 + 空读 `sleep(0.05)`**，单独连跑 3 次全过。

### 2.4 跨文件重复的摘要实现（`a170807` / `edb039a`）

`sha256(data).hexdigest()` 的**命名函数副本**共 6 处逐字相同（package_reader / skill_inbox /
resident / files-io / community-client / community-server）。全部收敛为 `system/path_guard.digest`
的 import 别名，守卫断言**必须是同一函数对象**（`is`）。
**教训**：`scan_duplicates.py` 只查同文件，跨文件的逐字重复要靠 grep 特征串搜。

### 2.5 README / Gitee 资料的事实性偏差

- 模块地图与 catalog 不一致 → 被 `test_community_docs.py` 抓到（守卫有效），改为**动态生成**。

## 三、本会话排除的「疑似隐患」（查过，不是问题，别再重复查）

### 3.1 根目录 `src/` 与 `agent/src/` 的双源疑点 —— **无风险**

现象：editable 安装的 `.pth` 指向 `D:\xm\OmniOperator\src`，而源码在 `agent/src/`，
看起来像「运行时导入旧副本」。

实测：两者是**同一 inode**（`os.stat().st_ino` 相同），即同一物理文件的两个目录入口
（目录重构时建立的兼容布局，`.gitignore` 第 41 行 `/src/` 有意忽略）。**单一存储，永远同步**。

```bash
uv run --no-sync python -c "
import os
print(os.stat('agent/src/omni/__init__.py').st_ino == os.stat('src/omni/__init__.py').st_ino)"  # True
```

### 3.2 截图截成「白天主题」—— 不是主题写错

根因：`ui/theme.js` 在 `localStorage.omni_theme` 未设置时**跟随系统** `prefers-color-scheme`，
而 **Playwright 默认 light**。产品本身默认深色（CSS 只认 `[data-theme="light"]`）。
修法：截图脚本显式 `new_page(color_scheme='dark')`。
**判定图片深浅用 PIL 像素采样，别用视觉模型描述**（它会把深色图说成"右侧面板浅色"）。

### 3.3 v10 迁移的 `DROP INDEX` 没有 `IF EXISTS` —— 不是 bug

`_SCHEMA_V10` 里 `DROP INDEX uq_outbox_live;` 无 `IF EXISTS`。但 v7 先建、v10 后删，
**迁移顺序保证不会在索引不存在时 DROP**；且**已发布迁移逐字节不改**是纪律红线。记录为
「防御性不足」，不改。
