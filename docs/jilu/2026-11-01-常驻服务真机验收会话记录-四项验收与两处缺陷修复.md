### 3. 撞出并修掉的两个缺陷

**缺陷 A（`02e0a0a`）：真机崩溃循环**

- 现象：`ServiceError: omni-heartbeat 记录指向运行中的进程，请先核验并停止`，每 10 秒一轮，
  运行态快照永远不写、告警永远看不到。
- 根因：`.venv\Scripts\python.exe` 是**会再 fork 一次真解释器的跳板**。守护 spawn 记的是跳板 pid，
  真正执行 `omni.channels.heartbeat` 的是跳板的子进程 → 子进程按 pid 认不出自己 → 报错退出 → 被再拉起。
- 修法：子进程可**认领父进程**的启动记录（pid+创建时间+exe 三元组全等才认，陌生活进程与 PID 复用都不认）；
  源码指纹改为**只标记不拒绝**（它覆盖整个 `agent/src`，并行改一个前端文件就让注册失败——那是版本提示不是身份问题）；
  失败尝试计入 `attempts`，只有连续稳定 300s 才清零（否则退避与 `restart_max_attempts` 形同虚设，`restart_given_up` 永远不会出现）。

**缺陷 B（`5355723`，本轮新撞出）：启动记录被守护的迟写改回跳板**

- 现象：`data/run/omni-heartbeat.pid` 里的 pid 指向 **venv 跳板**而不是真正在跑模块的进程；
  `source_confirmed` 变成 `false`。记录指向的进程不是真正干活的那个 → 停止授权、状态展示都跟着错。
- 根因：守护 spawn 之后落盘前要算源码指纹（哈希整个 `agent/src`，几百毫秒），
  **子进程抢先登记的那份记录会被守护随后的写入覆盖**。竞态窗口很大，经常发生。
- 修法：落盘前先看现有记录的 pid 是否在自己的**后代链**上（跳板 → worker 是两层，只判直接子进程不够——
  本会话第一版实现就是在这里被回归测试打回的）；是就保留 worker 那份记录，launch_id 不变。
- 真机复验：修复后重启心跳，spawn 出来的是跳板 58180，记录指向的却是真解释器 68044，`source_confirmed=true`。

## 三、隐患（排查会话重点看这里）

### A. 进程与生命周期

1. **venv python 是跳板**——这是本轮两个缺陷的共同根因。任何「记录里的 pid 是谁」的判断都要记住：
   记录应当指向**真正在跑模块的那个进程**（uv 的 `cpython-*.exe`），不是 `.venv\Scripts\python.exe`。
   核验方法：看记录里的 `executable` 字段。
2. **守护落盘前算源码指纹**（哈希整个 `agent/src`）→ 几百毫秒的竞态窗口。已用「后代链判定」收口，
   但**任何新增的落盘点**都可能重开这个窗口。
3. **DETACHED_PROCESS 脱离不了 job object**。服务用 `DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP` 起，
   只能脱离控制台。进程若跑在某个 job 里（IDE 终端、任务计划、CI、agent harness），job 一关成员全死。
   用户的机器上通过 `start.bat` 起（用户自己的终端）就没这个问题。
4. **机器上跑着的实例指向临时工作树**：工作台与三个服务的 `PYTHONPATH` 都指向 `.workbuddy/tmp/accept2`。
   删掉它 → 服务下一次重启会 import 失败。收尾见第四节。
5. **手动 `POST .../start` 不会重置 supervisor 的 `attempts`**：崩溃循环跑满上限后手动拉起服务，
   `restart_given_up` 告警还会挂着，要等连续稳定 300s 才清。

### B. 多会话协作与仓库操作（本轮真的踩了）

6. **并行会话会改写历史**（本轮：`40c90d6` → `48cbf20`）。**按旧 HEAD 建的索引一旦提交，会把对方的新改动回退**。
   正解：`git commit-tree <tree> -p <base>` 建对象（不动分支）+
   `git update-ref refs/heads/master <new> <old>`（**带旧值校验**）原子换指针；基线用 `HEAD~1`。
7. **真实 git 索引与 HEAD 不同步**：你提交完，对方下一次提交会用旧索引把你的改动顶掉。
   提交后要在**自己的路径**上 `git reset -- <paths>` 把真实索引对齐新 HEAD。
8. **构造索引时的两个行尾陷阱**：`git show HEAD:<path>` 会套用 `core.autocrlf` 的工作区转换（LF→CRLF），
   取基线必须用 `git cat-file blob HEAD:<path>`；`subprocess.run(input=..., text=True)` 在**写入侧**
   会把 `\n` 翻译成 `os.linesep`（Windows 上是 CRLF）——构造索引要**全程 bytes**。
   否则写回索引就是**整文件换行符变更**（本轮一次 diff 变成 5000+ 行）。
9. **`docs/HANDOFF.md` 的 blob 是 CRLF/LF 混合**（HEAD 里就有 14 个 CR）——构造时锚点不要带 `\n`。
10. 备用索引 `GIT_INDEX_FILE` + `git commit` 在 HEAD 被推进时同样会出错，用第 6 条的做法。

### C. 测试

11. **全量数字必须来自提交树自校验**（editable 安装会把主工作区的代码加载进来）。
    提交树跑法：`git worktree add --detach <临时目录> HEAD` + `PYTHONPATH=<worktree>/agent/src`，
    跑完 `git worktree remove --force`。数字写进台账时要注明取自哪种跑法。
12. **有真服务在跑时全量会 flaky**：`test_command_jobs` 的两个用例在机器负载高时失败，单独复跑通过。
    排查时若看到这两项失败，先确认是不是机器上跑着工作台/服务。
13. 有测试用**相对路径**定位源码（`Path("src/...")`），只在 `CWD=agent/` 时成立——从仓库根跑全量会误报。

### D. 功能语义

14. **NapCat「上次登录 X」是历史推断**：uin 来自 `onebot11_<号>.json` 文件名，登录过一次就永远在磁盘上。
