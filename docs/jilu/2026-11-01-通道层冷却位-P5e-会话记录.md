### 1.3 抄语义不抄形态：这一块到底抄了什么

参考源是 SurfCore 的 `conversation-closure.js`（523 行）。它用一整套**对话收尾状态机**
（六信号打分、`requireNoOpenQuestion`、摘要与下次开场白）回答「这段可以结束了」。

**我们不抄那套形态**，理由有三条，任一条都足以否掉整块移植：

1. 我们是**一问一答的无状态模型**，六信号打分的前提（有一份持续更新的对话状态）不成立；
2. NOTES §11.8 我们自己已经给了结论：**「可以在通道层加一个冷却位（收到消息后 N 分钟内不再主动搭话），
   不必上完整的状态机」**；
3. 抄一个前提不成立的机制，只会得到**没人调、没人敢删**的死代码。

**只抄它真正起作用的那一条判定**——`closureSuppressesWake(record, reason, now)`：

- 软唤醒 `SOFT_WAKE_REASONS` **才被压制**；
- 被 @ / 叫名字 / 提问 / 拍一拍 / 指定成员 / 私聊**一律不压**。

surfcore 源码里那句注释说得很准，本会话把它抄进了代码注释：

> 「结束不是把人关掉」

顺带抄了两个具体数值：`cooldownMs = 20min`（冷却窗口）、`idleThresholdMs = 30min`（目的引擎的
「主人刚聊过就不插话」）。后者是判断 cron 该不该被压制的依据（见 §2.2）。

### 1.5 暂存手法：共享文件用「构造索引」分离

本会话要碰的 5 个文件里，`config.py` / `bootstrap.py` / `core/cron.py` / `config.example.yaml` /
`docs/DEVELOPMENT_STATUS.md` 都在并行会话的改动面上。做法（脚本在
`.workbuddy/tmp/stage_d37.py`，**未入库**，可复用）：

1. `git show HEAD:<path>` 取基线（LF）；
2. 在基线上用**精确字符串替换**只重放「我的改动」，每个锚点**断言恰好命中一次**
   （命中 0 次或 2 次都直接报错退出，不静默跳过）；
3. `git hash-object -w --no-filters --stdin` 写 blob；
4. `git update-index --cacheinfo 100644,<sha>,<path>` 写进索引。

**工作区一个字不动**——并行会话的在途改动原地保留（对方工作区继续显示 modified，这是对的）。
暂存后逐文件核对 `git diff --cached`，确认共享文件里**只有我的 hunk**，没有他们的
`UpdateManager`、persona 场景层、`updates:` 配置段。

### 2.2 cron 到底算软唤醒还是硬唤醒（本会话自我纠错过一次）

第一次写成了**硬唤醒**，理由是「定时提醒是用户显式设定的任务，推迟会让提醒失真」。
**这个理由站不住**，复核后改成软唤醒：

- surfcore 目的引擎的 `idleThresholdMs = 30min`（「主人刚聊过就不插话」）管的正是这一类；
- cron 路径有 outbox，被压制时是**延迟补投**不是丢弃，提醒不会消失。

代价是：定时提醒**最多晚一个冷却窗口**送达（已写进台账的剩余限制 ③）。

### 2.3 为什么入站路径一个字都不用改

QQ 收到消息后的必然回复走 `channels/qq.py::_handle_batch`，**根本不经过主动闸门**。
所以把冷却判定挂在主动闸门上，就自动做到「潜水期照常回话、不主动搭话」——
**不需要在入站路径上再写一遍例外分支**。少一处例外就少一处漂移。

### 2.4 冷却锚点为什么复用 `qq_messages.created_at`（而不是新建表）

`qq_messages` 表（schema v12）已有 `(bot, scene, message_id, status, created_at REAL)`，
`created_at` 由 `QQMessageStore._insert` 写入 `self.clock()`。复用它 = **零 schema 变更** →
真机 `data/*.db` 结构不变 → **不需要 backup/迁移**（这正是本会话避开 `state_schema.py`
v15 冲突的原因）。且 `state.db` 天然跨进程共享：QQ 通道进程收消息写，心跳/工具进程读。

### 2.5 两条主动路径对「冷却中」的处置不同（这是刻意分开的）

| 路径 | 有队列吗 | `defer` 的实际效果 |
|---|---|---|
| cron 投递 | 有（outbox） | 留在队列里，每 60 秒重查策略，冷却结束自然补投 → **不丢内容** |
| 模型主动私聊 | 没有 | 转成一次明确拒绝，错误码 `proactive_cooldown` |

**所以冷却命中必须返回 `defer` 而不能是 `deny`**——deny 会让 cron 路径把消息直接丢掉。
`outbox.defer_claim` 做 `attempts = MAX(0, attempts-1)`，`claim_next` 先 +1，**净 0**，
所以等待不烧重试预算。

## 四、隐患清单

### 4.1 环境/协作类（本会话踩过或核实的，**优先级最高**）

1. **`.venv` 是 editable 安装，`.pth` 指向主工作区 `src`**——在 `git worktree` 里直接跑 pytest
   **加载的仍是主工作区的代码**，数字是混的，还会让断言仓库路径的测试必失败。
   正解：`git worktree add --detach <临时目录> <commit>` 且 `PYTHONPATH=<worktree>/agent/src` 重跑。
   本会话的全量数字就是这么取的。
2. **并行会话共享文件禁止 `git add .` / 整目录暂存**——`git add agent/src/omni` 会卷入同目录下
   并行会话的 46 个 web_static 版本串文件。用「构造索引」分离（§1.5）。
   误卷入的补救：`git reset --soft HEAD~1` + `git restore --staged <目录>`。
3. **索引会被并行会话的提交推旧**：自己提交后要按当前 HEAD 再重生成一次索引；
   `test_project_catalog.py` 会因索引与源码不符而失败。
4. **`git hash-object -w` 默认会走行尾过滤**——要存原始 CRLF 必须加 `--no-filters`；
   用 `--path=<path>` 会触发 clean filter 把 CRLF 转成 LF，结果是**整文件 diff**（四万行替换）。
   本仓库 `docs/index/*` 的 blob 存 CRLF，源码与 `docs/*.md` 存 LF——逐文件核对行尾。
5. **`git update-ref` 一定要带旧值期望**（`git update-ref <ref> <new> <old>`）——并行会话可能在你
   操作期间推进 master，带旧值校验失败就别硬推。
6. **不要 `git commit --amend`**：并行会话会在你 amend 期间推进 HEAD，amend 会把他们的提交吞掉。
   本会话因此把「全量测试数字」拆成**第二个提交**补录，而不是 amend 第一个提交。
7. **常驻服务必须由用户的进程树启动**：工具环境里的进程都在同一个 job object，工具调用一结束就
   连坐回收（`CREATE_BREAKAWAY_FROM_JOB` 被拒 `WinError 5`）。**要拉起常驻服务就让用户双击 `start.bat`**。
8. **本地接口探测要绕过系统代理**：环境里有 `HTTP_PROXY/HTTPS_PROXY`，urllib 走代理后请求
   `127.0.0.1:8000` 会拿到 502。Python 用 `ProxyHandler({})`，curl 用 `--noproxy '*'`。
9. **静态资源从磁盘读、API 路由启动时注册**——改了前端没重启工作台，会出现「UI 已生效、接口 404」
   的不一致状态。判断「新接口到底在不在」要先配对 `data/run/pair_url.json` 的码换 session cookie，
   否则全局鉴权一律回 401，看不出路由存不存在。
10. **PowerShell 读无 BOM 的 UTF-8 `.ps1` 按 ANSI**：文件里有中文会乱码并报「字符串缺少终止符」——
    写诊断脚本一律用纯 ASCII，或写成带 BOM 的 UTF-8。
11. **环境变量大小写重复键会炸 PowerShell**：同时存在 `https_proxy` 与 `HTTPS_PROXY` 时，
    `Get-ChildItem Env:` 与带 `-RedirectStandardOutput` 的 `Start-Process` 都会抛
    「已添加了具有相同键的项」。
12. **含转义（`\n`、`\t`）的文本一律用编辑工具写，不要用 shell heredoc**——heredoc 会把
    `"persona:\n  name: x"` 变成 `"persona:/n  name: x"`，YAML 直接解析失败。
13. **`docs/index/*` 是从脏工作区生成的，索引与提交树对不上（重要）**：核实发现 HEAD 里的
    `docs/index/MODULES.md` / `project.json` **已经写进了并行会话尚未提交的
    `agent/src/omni/system/updates/` 模块**（`git ls-tree HEAD agent/src/omni/system/` 里没有它，
    只在工作区里有）。也就是说：
    - 从**干净树**重生成索引 → 会把那些条目**删掉**（等于抹掉对方的成果）；
    - 从**主工作区**重生成 → 会把对方的在途代码混进我的提交；
    - 两头都不对。本会话因此**选择「不碰 + 写明」**（台账剩余限制 ⑧）。
    该索引**没有任何测试门禁**——`test_project_catalog.py` 校验的是 `build_index()` 函数与
    `/api/workbench/project` 接口，**不校验 `docs/index/*` 文件**，所以不碰它不会让测试变红。
    **待办**：等所有并行会话落盘、工作树干净时，统一重生成一次索引并提交。

### 4.2 本特性自身的限制（台账里也写了，这里再列一遍便于排查）

14. **`qq_messages` 只记入站不记出站** → 「我刚发过消息」**不刷新**冷却窗口。
    我方单方面说话时不会被自己锁住，但也不会因此延长冷却。
15. **冷却按 scene 锚定**（私聊 `dm:{target}`），**群场景不参与主动私聊冷却**。
    `dm_scene()` 必须与 `channels/qq.py::_resolve_scope` 的命名保持一致，否则永远查不到入站时间
    （表现为「冷却从不生效」）。
16. **cron 被压制时是延迟补投不是丢弃** → 20 分钟窗口内的定时提醒**会晚到**（最多晚一个窗口）。
17. **工作台的 QQ 策略面板不显示冷却状态**（`channels/web.py` 并行会话在改，本轮刻意不碰），
    用户只能从模型的拒绝文案里看到「冷却中」。
18. **`ProactiveDecision` 新增了 `code` 字段**：任何自己构造 `ProactiveDecision` 的地方
    （第三方插件、测试夹具）如果按位置传 5 个参数，第 5 个会被当成 `code`——目前仓库内只有
    `safety/proactive.py` 自己构造，**跨仓/插件侧需要留意**。
19. **`bot` 传 None 时跨 bot 聚合**：`bot id` 只有 QQ 通道从 `event['self_id']` 取得到，
    cron/工具两条主动路径手上没有它。scene 本身已按「私聊/群」命名空间隔离，
    一实例一 bot 的现实用法下等价；**多 bot 共用一个 state.db 时会不准**。
