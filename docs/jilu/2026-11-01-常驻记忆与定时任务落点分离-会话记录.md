## 五、隐患清单（排查会话重点看）

### 5.1 【最易误判】并行会话的提交会把**别人的**改动一起带走

本会话的 `MEMORY_POLICY`（`core/context.py`）在 `fea5b4a` 之前**就已经在 HEAD 里**，
是并行会话的提交 `40c90d6`（"拟人化：剩余限制核实与四项优化"）一并带进去的。
同样的，`docs/MEMORY_SYSTEM.md` 的 §1.1「写入落点：调度与记忆不得互相复制」
也是被并行会话的 `a89ce43` 带走的。

**后果**：看 `git log` 会以为「提示词早就写好了」，实际是**别的会话提交时顺手捎上的**。
排查时请用 `git log -S "<关键字符串>" -- <文件>` 追溯真实归属，别只看 `git blame` 的最终状态。

### 5.2 【本会话亲自踩到】混合文件提交必须用「构造索引」分离

`journal.py`、`people.py`、`config.example.yaml` 这三个文件，
**并行会话同时在改**（`updates` gate、场景层注释、ruff 格式化）。
直接 `git add` 会把对方的在途改动一起提交。

**本会话的做法**（可复用）：以 `git show HEAD:<path>` 为基线，只重放**本会话**的改动，
再 `git hash-object -w --stdin` + `git update-index --cacheinfo 100644,<sha>,<path>`
写进索引；**工作区一个字不动**，对方的在途改动原地保留（提交后该文件显示为 `MM`，
这是对的）。

配套的三条纪律：
1. **字符串替换必须断言「恰好命中一次」**，命中不到就报错退出，别静默跳过；
2. **`git hash-object -w --stdin` 不带 `--path` 时不做行尾过滤**——用它才能存原始字节。
   本会话三个文件的 HEAD blob 都是纯 LF（CR=0），工作区是 CRLF（`core.autocrlf=true`）；
   加 `--path` 会触发 clean filter，**整个文件会变成全行替换的假 diff**；
3. 提交后 `git diff --cached --name-only | grep web_static` 必须为 0。

### 5.3 【易踩】两个 pytest 同时跑会造出「大面积失败」的假象

见 §2.3。本会话一度以为全量挂了 200 多项，实际是自己开了两个 pytest 互相踩。
**同一仓库只跑一个 pytest**，这是多会话环境里的高频陷阱。

### 5.4 【易踩】`test_runs.py::test_cancel_is_cooperative...` 是负载型 flaky

见 §2.4。2 秒的注册等待预算，机器 busy 时会失败。**排查时先看机器负载再归因**。

### 5.5 【本次未处理】`docs/index` 当前 stale（属并行会话）

实测 `python scripts/project_index.py --check` → `stale=MODULES.md,project.json`。
原因是并行会话新增了 `system/updates/`、`http-updates` 两个模块（catalog schema 与
README 模块地图都已补，`test_community_docs.py` 9 项全绿），但**索引尚未按新模块重生成**。

**按项目约定，索引应由提交它的一方在干净工作树上重生成**

本会话**没有**动模块结构，**不负责**重生成——但排查会话应确认这一项最终被谁补上。
