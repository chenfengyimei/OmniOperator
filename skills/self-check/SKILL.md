# self-check（任务完成自查）

## When to Use（何时用）

- 任何**多步任务**收尾阶段（工具调用 ≥3 次、或涉及多个文件/多个数据源）之后，回复用户之前
- 用户提出"帮我搞定/做完/全部处理一下"这类需要交付结果的请求
- 做过有副作用的操作（写文件、发消息、改配置、创建技能/记忆）之后
- 踩坑后重试成功时：自查一遍，确认没有留下半成品或脏数据

> 原则：自查是**回答前的最后一道关**，不是可选项。哪怕任务看起来"显然成功"，也要过一遍三问。

## Procedure（步骤）

### 1. 步骤完整性核对（做全了吗？）
- 回放最初请求，把用户的**每一句需求拆成条目**（含隐含需求，如"顺便整理一下"）
- 对照实际执行的调用链，逐条打勾：需求 → 对应动作 → 是否覆盖
- 特别检查**容易漏的尾巴**：多个对象时是否只处理了第一个？条件分支是否只走了一侧？分页/多条结果是否只取了首页？
- 依赖关系是否按序完成（先查后改、先读后写）

### 2. 结果正确性核对（做对了吗？）
- 用**独立证据**验证，而不是"我调用了工具 = 成功了"：工具返回值里是否有 success/错误字段、条数是否合理、关键字段是否为空
- 抽样核对内容：数字/名称/ID/路径/链接与来源是否一致，有没有把示例值、占位符、相似但不同对象搞混
- 检查推理链的假设：是否依赖了未验证的前提（如"默认用户想要 X 格式"）
- 边界情况：空结果、超时、权限失败、编码乱码，是否被误当成成功
- 有副作用时确认**作用对象正确**（改的是目标文件/目标条目，没误伤别处）

### 3. 遗留事项清点（还剩什么？）
- 明确列出：未完成的子任务、被跳过的部分及原因、需要用户确认的决策点
- 外部依赖/等待项（需要用户提供信息、需要后续跟进的时间点）
- 副作用残留：临时文件、测试数据、创建后不再需要的技能/记忆、部分应用失败的改动
- 判断哪些该在**回复里明说**，哪些需要用户下一步动作

### 4. 汇总与修复
- 发现缺口就先补，补不了的诚实说明
- 回复结构：**做了什么 → 结果与证据 → 遗留/需你确认的事项**，不夸大完成度
- 若同类缺口反复出现，把经验补进对应技能或写成新技能

## Pitfalls（坑）

- **把"工具没报错"当成"任务成功"**：很多工具失败是静默的（返回空列表、默认值），必须查业务字段
- **只自查自己想得起来的部分**：要按用户原始请求逐句过，不是按自己的执行顺序过
- **自查变成自我表扬**：只找"我做得挺好"的证据。要主动找反例："如果这里错了，会在哪儿露出来？"
- **报喜不报忧**：把未完成部分藏进"已完成"的描述里，是最严重的失败模式
- **过度自查导致不交付**：自查控制在 1 轮、抓关键项；三问过完就回复，别无限循环
- **多对象任务只验第一个**：批量操作要验首尾两个 + 数量对得上

## Verification（怎么验证做对了）

- 每个用户需求条目都能指到**具体一次调用 + 具体一处证据**，无空条目
- 结果核对至少用了 1 个**独立于操作本身**的检查（回读、计数、字段比对）
- 回复中包含遗留事项段落（哪怕内容是"无"）
- 自问三句都能答上来：**需求都覆盖了吗？结果有证据吗？还有什么没交代？**
